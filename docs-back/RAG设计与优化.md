## 平行宇宙人生模拟器 - RAG 设计与优化说明

> 本文档用于系统性说明本项目中 RAG（Retrieval-Augmented Generation，检索增强生成）的整体方案、关键原理、实现细节与优化策略，可直接作为简历补充材料或面试时的深度讲解参考。

---

## 1. 项目中为什么要用 RAG？

- **业务场景特点**：本项目聚焦「人生规划 / 职业决策」场景，回答需要兼具专业性、连贯性和可解释性，不能只靠大模型的“常识印象”。
- **纯 LLM 的问题**：
  - 容易产生「幻觉」（看起来很专业，但没有依据）。
  - 难以注入项目内沉淀的专业资料和自有知识。
  - 模型升级或更换时，知识迁移成本高。
- **RAG 带来的价值**：
  - 把业务领域知识沉淀为可检索的知识库，回答有“出处”。
  - 通过检索控制上下文，降低幻觉概率。
  - 能在不重新训练大模型的前提下持续迭代知识库。

一句话概括：**RAG 让大模型“带着项目自己的知识说话”，而不是只靠通用预训练记忆。**

---

## 2. 整体架构与数据流

从架构视角看，本项目的 RAG 分为「离线构建」和「在线查询」两大阶段：

1. **离线构建阶段**
   - 收集并清洗人生规划 / 决策分析 / 职业路径等文档。
   - 按语义切分为多个 chunk，生成向量并存入 PostgreSQL + pgvector。
   - 构建向量索引（如 HNSW），并对部分热点数据做缓存预热。

2. **在线查询阶段**
   - 用户在前端发起对话（可选择 `useRag = true`）。
   - 后端对用户问题做向量化，使用 pgvector 做 Top-K 语义检索。
   - 将检索结果通过 Spring AI 的 Advisor（如 `QuestionAnswerAdvisor`）注入 Prompt。
   - ChatClient 调用大模型，在携带检索上下文和历史对话的情况下生成回答。
   - 返回给前端（支持 SSE 流式和一次性返回两种模式）。

用一句路线图来概括在线流程：

> **Query → Embedding → Vector Search (pgvector + Redis 缓存) → Context Assembly → LLM (Spring AI) → Answer / Report**

## 3. 核心原理拆解

### 3.1 文本向量化的原理

- **Embedding 是什么？**
  - 把一段文本映射到一个高维向量空间（例如 768 维或 1024 维），相似语义的文本，其向量距离会比较近。
  - 可以理解为：模型在「语义空间」中给每个句子一个坐标。

- **本项目如何使用 Embedding？**
  - 使用 Spring AI 集成的向量模型，对「文档块（chunk）」和「用户查询」分别生成向量。
  - 存储时，将每个 chunk 的向量写入 pgvector 字段；查询时，对用户问题生成向量，然后在向量空间内做近邻搜索。

- **相似度计算（以余弦相似度为例）**
  - 设两个向量分别为 \( \mathbf{u}, \mathbf{v} \)，则余弦相似度为：
    \[
      \text{cos\_sim}(\mathbf{u}, \mathbf{v}) = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\| \cdot \|\mathbf{v}\|}
    \]
  - 值域为 \([-1, 1]\)，越接近 1 表示语义越接近。
  - pgvector 内部实现会对向量做归一化处理，以提高效率和数值稳定性。

### 3.2 pgvector 与 ANN（近似最近邻）检索

- **为什么不用「全表扫描 + 精确最近邻」？**
  - 假设知识库中有 N 条向量记录，精确最近邻需要计算每条记录与查询向量的距离，时间复杂度为 \(O(N \cdot d)\)（d 为向量维度），数据量一大，延迟无法接受。

- **pgvector 提供的优化：**
  - pgvector 扩展在 PostgreSQL 中引入了 `vector` 类型和相似度操作符（如 `<->`）。
  - 支持多种索引结构，其中常用的是 **HNSW（Hierarchical Navigable Small World）**。

- **HNSW 原理简述：**
  - 构建一个分层图结构，底层连接最密集、上层连接稀疏。
  - 查询时，从上层开始“跳跃式”地寻找更近的节点，逐步往下层细化搜索。
  - 这样可以在接近对数时间复杂度内找到近似最近邻，牺牲少量精度换取大幅性能。

> 对面试官可以这样解释：**pgvector 通过 HNSW 等 ANN 索引，把「找最相似文档」这件事从“全库一条条比”变成“在一个聪明的图里走几步路就能找到附近的点”，因此延迟从秒级降低到了百毫秒级。**

### 3.3 RAG 生成流程的本质

从数学视角看，RAG 不是直接学习一个「回答函数」，而是拆成两步：

1. **检索阶段：** 根据查询 \(q\)，从知识库 \(D\) 中找到一组相关文档 \( \{d_1, d_2, ..., d_k\} \)。
2. **生成阶段：** 令大模型在条件 \(q, d_1, d_2, ..., d_k\) 下，输出回答 \(a\)，即：
   \[
     a = \text{LLM}(q, d_1, d_2, ..., d_k)
   \]

这样，大模型主要解决「如何组织语言、如何推理」的问题，而「事实性知识」则由检索阶段提供和约束。

## 4. 离线阶段：知识库构建流程

### 4.1 数据源与清洗

- **数据来源**：
  - 人生规划方法论、决策分析框架、职业发展路径等内部整理文档。
  - 高质量外部资料（书籍、课程、文章），经过人工筛选与归档。
- **清洗步骤**：
  - 统一编码与文本格式，去掉页眉页脚、目录页、广告等噪声。
  - 合并过短句子，保证 chunk 具备完整语义。
  - 为每一段打上 metadata：`topic`（主题）、`sub_topic`、`source`、`level`、`updated_at` 等。

### 4.2 文本切分（Chunking）设计

- **设计目标**：既要保证单个 chunk 语义足够完整，便于模型理解，又要控制长度避免浪费 token。
- **策略选择**：
  - 字数维度：单块控制在 **500–1000 字** 范围内。
  - 采用「语义切分 + 滑动窗口」：
    - 先按章节 / 小节做语义切分。
    - 对于过长段落，使用固定窗口（如 800 字）+ 重叠（如 200 字）进行二次切分。
  - 重叠的意义：避免关键句刚好跨 chunk 边界而被分割。

### 4.3 向量化与写入存储

- **向量生成**：
  - 对每个 chunk 构造 embedding 输入：`[标题] + [关键标签] + [正文]`。
  - 使用 Spring AI 的 Embedding 接口调用向量模型，得到 d 维向量。
- **写入 PostgreSQL + pgvector**：
  - 建表时字段示例：
    - `id`：主键。
    - `content`：原文。
    - `metadata`：JSON（topic、source、level...）。
    - `embedding`：`vector(d)`。
  - 为 `embedding` 字段建立 HNSW 索引或 IVF 索引，配置适当的 `m`、`ef_construction` 等参数。

## 5. 在线阶段：一次 RAG 对话的完整链路

以「开启 RAG 增强的普通对话」为例，流程可以拆成以下步骤：

1. **前端请求**
   - 调用类似 `/parallel-life/chat/stream` 的接口，Body 中包含：
     - `message`：用户问题。
     - `chatId`：会话 ID。
     - `useRag = true`。

2. **Controller / Service 层**
   - 参数校验，将请求封装为 `ChatRequest`。
   - 根据 `useRag` 标志，路由到 RAG 对话方法，例如：
     - 同步：`doChatWithRag(message, chatId)`。
     - 流式：`doChatWithRagStream(message, chatId)`。

3. **查询向量生成**
   - 调用 Embedding 模型对 `message` 生成查询向量 \( \mathbf{q} \)。
   - 对文本可做轻量归一化，如：
     - 转小写、去除多余空白。
     - 可以视情况移除停用词（但中文通常不强制）。

4. **缓存预查（Redis）**
   - 先按 `hash(normalized_message)` 构造缓存 key：`RAG:QUERY:{hash}`。
   - 命中：直接得到候选文档 ID 列表（和部分预处理结果）。
   - 未命中：进入数据库检索流程。

5. **向量检索（pgvector）**
   - 在 PostgreSQL 中使用类似语句：
     - `ORDER BY embedding <-> q_vector LIMIT k;`
   - 这里 `<->` 表示向量距离操作符，具体含义取决于选用的度量（如余弦、L2 距离）。
   - 使用 HNSW 索引加速查询，`LIMIT k` 对应 Top-K。

6. **重排序与阈值过滤**

   目的：提高「相关但不冗余」的检索质量。

   - 设置一个相似度（或距离）阈值，过滤掉得分太低的结果。
   - 在得分相近的结果中，可根据 metadata 再排序，例如：
     - 更接近当前对话主题的优先。
     - 更近期的内容优先。
     - 来源更权威的优先。
   - 最终选取 3–5 个文档块作为候选上下文。

7. **Prompt 构造（Spring AI Advisor）**
   - 利用 `QuestionAnswerAdvisor` 将检索到的文档注入 Prompt，大致结构为：
     - System Prompt：定义模型角色（人生规划顾问）、约束输出格式和风格。
     - Context Section：拼接若干个「参考资料」片段，每个片段附带来源信息。
     - Conversation History：通过 `ChatMemory` 注入历史对话（例如最近 10 轮）。
     - User Question：当前用户问题。

8. **模型推理（非流式 / 流式）**
   - 非流式：
     - 调用：`chatClient.prompt().user(message).advisors(...).call().chatResponse()`。
     - 读取 `chatResponse.getResult().getOutput().getText()` 作为最终回答。
   - 流式（SSE）：
     - 调用：`chatClient.prompt().user(message).advisors(...).stream().content()`。
     - 得到 `Flux<String>`，逐 token 或逐片段推送到前端。

9. **回答返回与日志记录**
   - 对结果进行结构化封装（code/message/data），统一响应格式。
   - 打上 TraceId，记录检索结果和核心指标（检索耗时、缓存命中、Top-K 等），用于后续优化和问题排查。

## 6. 性能优化策略与实测效果

### 6.1 检索性能优化

1. **ANN 索引（HNSW / IVF）**
   - 相比无索引的顺序扫描，ANN 将延迟从 \(O(N)\) 降到接近 \(O(\log N)\)。
   - 通过调参平衡：
     - 索引构建时间与索引大小。
     - 检索速度与召回率。

2. **Top-K 与阈值调优**
   - 通过线下实验发现：
     - `TopK=3~5` 在「信息充分 + 成本可控」之间较为平衡。
     - 并设置「相似度下限」，避免非常边缘的文档被误注入上下文。

3. **Redis 缓存策略**
   - 高频问题（如“如何做职业规划”、“怎么做职业选择对比”等）检索结果高度可复用。
   - 在 Redis 中缓存：
     - 查询向量的检索结果（文档 ID + 排序得分）。
     - 甚至可以缓存已经组织好的「参考资料片段字符串」，进一步节省 CPU。
   - TTL 一般设置为 30–60 分钟，通过监控观察命中率与内存占用。

**效果示例（可在简历或面试中使用）：**

- RAG 检索平均耗时从 **1–2 秒** 优化到 **200–300 ms**。
- 在缓存命中场景下，平均耗时进一步下降到 **几十毫秒级**。
- 整体对话接口 P95 响应时间控制在 **2 秒以内**。

### 6.2 Prompt 与 Token 成本控制

- 控制每次注入的文档数量和长度，只保留：
  - 与问题高度相关的 3–5 个 chunk。
  - 每个 chunk 截断到关键段落，避免无效长尾内容。
- 对报告生成场景（如 `ParallelLifeReport`）：
  - 使用结构化输出（`.entity()`），减少模型在格式上的浪费。
  - 通过合理的字段设计，使得模型只输出必要字段，避免冗余文本。

### 6.3 并发与连接池优化

- 对 PostgreSQL 使用 HikariCP 连接池，按实际 QPS 与机器核数调节：
  - `maximumPoolSize`、`minimumIdle`、`connectionTimeout` 等参数。
- 对 Redis 使用连接池，并配合合理的超时与重试策略。
- 对模型调用使用异步 / 响应式方式（如 WebFlux + Reactor），使线程不被长时间 I/O 阻塞。

## 7. 回答质量与稳定性控制

### 7.1 Prompt 工程要点

- 在 System Prompt 中明确要求：
  - **优先基于提供的参考资料回答**，无法覆盖时可以补充通用经验，并显式说明。
  - 回答要有结构（列表、步骤、对比），避免大段散文式输出。
  - 在涉及建议类回答时，区分「事实」与「推断」，减少绝对化表述。

### 7.2 RAG Fallback 策略

当检索结果不理想（无结果或得分低于阈值）时：

- 对用户做「信息透明」：
  - 明确提示：“当前知识库中没有很匹配的内容，我将基于通用经验给出一些建议，仅供参考。”
- 可选择两种策略：
  - 切换到纯 LLM 模式，让模型基于自身知识回答。
  - 要求模型反问用户、收集更多信息后再尝试回答。

这样可以在保持用户体验的同时，减少「看似有依据但实际上没有检索依据」的回答。

### 7.3 结构化输出与验证

- 对报告类场景（如平行人生报告）：
  - 设计 Java 实体类 `ParallelLifeReport`、`Universe` 等，约束字段和层级结构。
  - 使用 Spring AI 的 `.entity(ParallelLifeReport.class)` 解析模型输出。
  - 对关键字段做非空 / 长度 / 枚举校验，发现异常时回退到兜底回答或重新生成。

## 8. 监控与评估体系

### 8.1 技术指标监控

- 检索相关指标：
  - RAG 检索耗时 P50 / P95。
  - Redis 缓存命中率。
  - 每次回答使用的参考文档数量、总 token 数。
  - 向量库错误率（超时、连接失败等）。
- 模型调用相关指标：
  - 请求成功率、超时率。
  - token 消耗量（prompt / completion）。
  - 接口整体响应时间。

### 8.2 业务效果评估

- 用户反馈：
  - “这次回答是否有帮助？”的简单二元反馈。
  - 用户是否再次追问同一问题（隐含对第一次回答的不满意）。
- 报告阅读行为：
  - 前端埋点统计报告是否被完整浏览（滑动到末尾、停留时长等）。

通过这些数据，可以闭环优化：

- 针对低满意度问题回溯检索日志，分析是否是：
  - 检索召回不足。
  - Prompt 约束不合理。
  - 报告模板设计问题。

## 9. 面试话术示例：如何三五分钟讲清本项目的 RAG

> 在这个项目里，我落地了一套基于 PostgreSQL + pgvector 的 RAG 方案。离线部分把人生规划相关文档做了清洗和语义切分，通过 Spring AI 的 embedding 接口生成向量，并存入带 HNSW 索引的 pgvector 表中；在线部分，对用户问题先做向量化，然后用 pgvector 做 Top-K 语义检索，再把检索到的 3–5 条高相关片段通过 Advisor 注入到 Prompt 里，结合 ChatMemory 的多轮上下文，最终由大模型生成回答或结构化报告。
>
> 性能上，一方面依赖 pgvector 的 ANN 索引，另一方面对高频查询结果做 Redis 缓存，把 RAG 检索的 P95 延迟压到了 500ms 以内，整体对话接口的 P95 控制在 2s 左右。质量上，通过检索阈值、Fallback 策略和结构化输出，尽量减少幻觉并保证报告格式稳定，这一块在面试中可以单独展开细节。

- 在工程实现上，充分利用了 Spring AI、pgvector、Redis 等组件的特性，实现了一个既可扩展又成本可控的知识增强系统。

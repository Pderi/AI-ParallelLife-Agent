# 上下文管理改造方案（三层记忆 + Self-Healing Memory）

## 1. 改造背景
当前项目中，`BaseAgent` 通过 `messageList` 在内存维护会话上下文，这种方式实现简单，但在以下场景会遇到瓶颈：

1. 对话轮次变多后，上下文膨胀导致 token 成本上升、响应变慢。
2. 会话结束后缺乏结构化沉淀，历史经验无法稳定复用。
3. 长期历史检索能力不足，难以实现“按需召回”。
4. 缺少记忆“新鲜度管理”，容易出现过期记忆干扰推理。

本方案目标是把上下文管理升级为三层记忆体系：**热数据常驻、温数据按需、冷数据可检索**，并引入自愈机制，持续优化记忆质量。

---

## 2. 目标与原则
### 2.1 目标
1. 让 Agent 在多轮对话中保持稳定上下文感知能力。
2. 控制上下文体积，降低 token 成本与延迟。
3. 让经验可沉淀、可更新、可淘汰，避免“记忆腐化”。
4. 为后续高并发场景提供可扩展的上下文加载路径。

### 2.2 原则
1. **分层管理**：不同温度的数据用不同存储与加载策略。
2. **按需加载**：只有当前任务相关内容才进入上下文。
3. **可解释**：每次召回都能说明“为什么被选中”。
4. **可治理**：有版本、有 TTL、有质量评分与淘汰机制。

---

## 3. 三层记忆架构设计

### 3.1 第一层：热记忆（Hot）——入口索引
建议形态：`memdir/MEMORY.md`

作用：
1. 常驻加载，类似“目录页 + 高价值指针”。
2. 不存大段正文，只存摘要、索引、约束、关键规则与 topic 文件指针。
3. 保持轻量，避免挤占主上下文窗口。

建议约束：
1. 行数上限：`<= 200` 行。
2. 体积上限：`<= 25KB`。
3. 内容结构固定，便于模型稳定解析。

建议内容模板：
- Agent 核心行为约束（必须遵守的系统规则）
- 当前项目关键模块索引（例如上下文、工具调用、RAG、异常处理）
- 高风险坑位清单（known issues）
- Topic 文件列表（只放文件名、标签、更新时间、优先级）

---

### 3.2 第二层：温记忆（Warm）——话题文件
建议目录：`memdir/topics/*.md`

作用：
1. 沉淀“稳定但非每轮必需”的知识：架构约定、编码偏好、常见故障、业务术语、关键决策。
2. 在每轮请求前，由“小选择器”从多个 topic 文件中挑选最多 `N` 个加载（建议 `N=3~5`）。
3. 避免一次性塞入全部历史，减少上下文噪声。

每个 topic 文件建议带 `frontmatter` 元信息：
- `id`: 唯一 ID
- `title`: 标题
- `tags`: 标签
- `priority`: 优先级（high/medium/low）
- `ttl_days`: 有效期
- `last_verified_at`: 最近人工或自动校验时间
- `quality_score`: 质量分（0-1）
- `source`: 来源（人工沉淀/会话提炼/系统生成）

加载策略（建议）：
1. 先基于 query 和任务类型算相关度。
2. 再叠加优先级、质量分、时效性打分。
3. 选择 top-N，超过预算则截断低分文件。

---

### 3.3 第三层：冷记忆（Cold）——原始历史对话
建议目录：`memdir/raw/*.jsonl`

作用：
1. 保存完整历史会话与关键执行轨迹（原始证据层）。
2. 默认不加载到 prompt。
3. 只有当热/温层无法回答，才进行关键词检索召回。

检索策略（建议）：
1. 首选关键词检索（时间范围 + tag + session + term）。
2. 返回候选片段后进行二次摘要压缩，再注入上下文。
3. 严格限制注入片段数量和字节大小，避免冷数据污染当前推理。

说明：
- 本阶段优先用关键词检索（实现简单、成本低、可控）。
- 后续再按收益决定是否引入向量检索，不必一开始上复杂 RAG。

---

## 4. Self-Healing Memory（记忆自愈机制）
自愈目标：让记忆“越用越准”，并能自动处理过期、冲突、冗余信息。

### 4.1 自愈触发时机
1. 每次会话结束后（异步任务）。
2. Topic 被多次命中但效果差（质量分下降）。
3. 发现冲突规则（新记忆与旧记忆矛盾）。
4. 周期性维护任务（如每日/每周）。

### 4.2 自愈动作
1. **提炼**：从 raw transcript 提取稳定经验，候选写入 topic。
2. **去重**：语义近似条目合并，保留高质量版本。
3. **降级**：过期或低置信内容从 warm 降级到 cold。
4. **淘汰**：长期低命中且低质量内容归档或删除。
5. **回写索引**：更新 `MEMORY.md` 的指针、优先级与 warning。

### 4.3 质量评分建议
`quality_score = 命中收益分 - 错误干扰分 - 过期惩罚`

可观测输入：
- 命中后回答质量是否提升
- 被用户纠正次数
- 导致 hallucination 或错误工具调用次数
- 最近验证时间

---

## 5. 与当前项目的对接方案（基于 BaseAgent）

### 5.1 现状
`BaseAgent` 当前在 `run()` 内直接维护 `messageList`，没有外部记忆加载/沉淀流程。

### 5.2 改造后职责拆分（先设计，后编码）
建议新增上下文管理器 `ContextManager`，由它统一处理三层记忆：

1. `ContextManager.buildContext(request)`
   - 读取 `MEMORY.md`（热层）
   - 选择 top-N topic（温层）
   - 必要时检索 raw transcript（冷层）
   - 输出最终 prompt context 包

2. `ContextManager.afterRun(sessionResult)`
   - 异步提炼本轮会话
   - 更新 topic 文件
   - 更新 MEMORY 索引
   - 写入 raw transcript

3. `BaseAgent` 仅负责编排执行循环，不再直接承载记忆策略细节。

### 5.3 建议模块结构
- `context/`
  - `ContextManager.java`
  - `MemoryLoader.java`（热/温/冷读取）
  - `TopicSelector.java`（相关度 + 规则选择）
  - `MemoryHealer.java`（自愈流程）
  - `MemoryPolicy.java`（预算、阈值、TTL）
- `memdir/`
  - `MEMORY.md`
  - `topics/*.md`
  - `raw/*.jsonl`

---

## 6. 数据规范建议
### 6.1 `MEMORY.md` 结构建议
1. 固定头部：项目目标、行为准则、禁忌清单。
2. Topic 索引区：仅放摘要 + 指针 + 优先级 + 更新时间。
3. Warning 区：截断或降级提示，帮助模型识别“索引不完整”状态。

### 6.2 Topic 文件规范
1. 一文件一主题，避免“超大杂烩”。
2. 每条经验包含：场景、决策、原因、反例。
3. 保留“已知坑位”而非仅保留“正确做法”。

### 6.3 Raw Transcript 规范
1. `jsonl` 按会话逐条追加，包含 `sessionId`, `timestamp`, `role`, `content`, `toolCalls`。
2. 对敏感信息脱敏后落盘。
3. 支持按 session 与日期范围快速过滤。

---

## 7. 上下文构建流程（请求时）
1. 接收用户请求并识别任务类型（问答/代码/规划/调试）。
2. 加载热层 `MEMORY.md`。
3. 基于 query 选择温层 top-N topic。
4. 判断是否需要冷层检索（仅在信息缺口时触发）。
5. 在 token 预算内组装上下文包：
   - system rules
   - selected topics
   - optional cold snippets
   - 当前用户输入
6. 执行 Agent 推理并记录可观测数据。

---

## 8. 上下文沉淀流程（请求后）
1. 保存本次对话到 raw transcript。
2. 提取候选经验（规则、偏好、坑位、FAQ、决策）。
3. 与现有 topic 比对：更新/合并/新建。
4. 更新 `MEMORY.md` 索引（指针 + 热度 + warning）。
5. 运行质量打分与 TTL 检查，触发降级/淘汰。

---

## 9. 并发与性能建议（与本方案配套）
1. 上下文构建与会话执行解耦：请求线程只做必要加载，沉淀与自愈异步化。
2. topic 选择与冷检索设置超时，超时则降级为“仅热层+当前输入”。
3. 对 `MEMORY.md` 和热点 topic 做本地缓存（短 TTL），降低磁盘 IO。
4. 写入 raw transcript 采用异步队列，确保高并发下不阻塞主链路。
5. 记忆文件更新采用乐观锁或版本号，避免并发写覆盖。

---

## 10. 上下文压缩管线（五级 Compact）
在三层记忆之外，建议增加“五级压缩管线”控制上下文体积，避免长会话导致 prompt 爆炸。

### 10.1 目标
1. 在不明显损失任务正确率的前提下，持续压缩上下文。
2. 让压缩具备可回退、可观测、可熔断能力。
3. 在高并发场景下降低 token 消耗与模型时延。

### 10.2 五级压缩策略
1. **Snip（剪裁）**
   - 作用：删除明显过期、与当前任务无关的对话片段。
   - 场景：会话轮次过多、最近上下文重复度高。
   - 要点：优先保留最近轮次、工具调用结果和未完成任务线索。

2. **Microcompact（微压缩）**
   - 作用：把工具结果、日志片段、长文本响应压缩为结构化摘要写入磁盘（而非全部驻留上下文）。
   - 场景：工具返回过大文本（例如长 JSON、检索长段落）。
   - 要点：保留“结论 + 关键证据 + 文件指针”，避免丢失可追溯性。

3. **Collapse（折叠）**
   - 作用：对中间对话块进行阶段性摘要，把多轮往返折叠为“目标-行动-结果-未决事项”。
   - 场景：任务跨多轮推进，历史中间过程冗长。
   - 要点：折叠后保留原始片段 ID，支持按需展开。

4. **Autocompact（自动全量压缩）**
   - 作用：当 token 或字节预算接近上限时，自动触发全局压缩。
   - 场景：上下文空间不足，继续注入会导致截断风险。
   - 要点：按优先级压缩（先冷后温再热），并写入压缩报告（删除/折叠了什么）。

5. **Reactive（反应式压缩）**
   - 作用：当出现上下文相关错误（如上下文窗口溢出、模型拒绝、413 类错误）时紧急降载压缩。
   - 场景：运行时异常触发。
   - 要点：快速降级为“热层 + 最近关键片段 + 当前请求”，优先恢复可用性。

### 10.3 触发条件（建议）
1. `token_usage > 70%`：进入 Snip/Microcompact 预处理。
2. `token_usage > 85%`：触发 Collapse。
3. `token_usage > 92%`：触发 Autocompact。
4. 出现窗口溢出或请求体过大错误：触发 Reactive。

### 10.4 失败保护与断路器
1. 压缩任务连续失败超过阈值（建议 3 次）后自动熔断，停止进一步压缩，回退安全策略。
2. 熔断期间使用最小上下文模板：`MEMORY.md + 最近 5 个关键片段 + 当前输入`。
3. 压缩后自动恢复最近关键文件指针，避免任务漂移。
4. 记录压缩失败原因与上下文快照摘要，便于后续修复策略。

### 10.5 与三层记忆的协同
1. Snip/Collapse 优先作用于“会话内临时上下文”。
2. Microcompact 产物优先沉淀到 warm/cold 层，避免重复注入。
3. Autocompact 不压缩 `MEMORY.md` 核心规则区，只压缩低优先级内容。
4. Reactive 模式下可临时跳过冷层检索，先保证主流程成功。

### 10.6 可观测指标（压缩专项）
1. 压缩触发率（分级别统计）。
2. 压缩后 token 降幅中位数与 P95。
3. 压缩后任务成功率变化。
4. 压缩失败率与熔断次数。
5. 压缩带来的平均时延与成本收益。

## 11. 风险与规避
1. **风险：topic 过多导致选择不稳**
   - 规避：限制总量，定期合并同类主题，强制 TTL。
2. **风险：错误记忆被强化**
   - 规避：引入质量分与人工审核入口，低质量自动降级。
3. **风险：冷数据召回噪声大**
   - 规避：严格关键词过滤 + 二次摘要 + 注入预算限制。
4. **风险：并发下文件冲突**
   - 规避：分片存储、版本控制、异步串行写入。

---

## 12. 分阶段落地计划（仅文档阶段）

### Phase 1：结构搭建（1 周）
1. 定义 `memdir` 目录规范与文件模板。
2. 完成 `MEMORY.md` 初版和若干 topic 样例。
3. 明确上下文预算与选择规则（N、TTL、score）。

### Phase 2：读取链路（1 周）
1. 在请求前引入热/温层加载逻辑。
2. 增加冷层关键词检索兜底。
3. 建立日志埋点（加载命中率、耗时、上下文大小）。

### Phase 3：沉淀与自愈（1~2 周）
1. 会话后异步写 raw transcript。
2. 自动提炼 topic 候选与去重合并。
3. 引入质量分、降级与淘汰策略。

### Phase 4：优化与治理（持续）
1. 评估是否引入向量检索增强冷层。
2. 增强可观测面板（命中质量、成本、时延）。
3. 建立人工审核机制，形成“自动 + 人工”双轨治理。

---

## 13. 验收指标（建议）
1. 平均上下文 token 降低 30% 以上。
2. 多轮任务成功率提升（可按业务定义）。
3. 平均响应时延下降（P95）。
4. 冷检索触发率可控（避免过度依赖冷层）。
5. 自愈后 topic 命中收益持续提升（按周观察）。

---

## 14. 结论
该改造方案本质上是把“消息列表记忆”升级为“分层知识操作系统”：

- 热层提供稳定入口与核心规则；
- 温层提供任务相关经验；
- 冷层提供可追溯原始证据；
- 自愈机制保证记忆随项目演进持续变好。

这套方案可以在不大改业务逻辑的前提下，先从上下文管理切入，逐步支撑你后续的大厂级 Agent 能力与高并发目标。

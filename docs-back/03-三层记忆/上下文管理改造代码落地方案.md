# 上下文管理改造代码落地方案（结合现有代码与数据持久化）

## 1. 目标与范围
本文用于将《上下文管理改造方案-三层记忆与自愈机制》落地到当前后端代码，强调“小步可验证”。

本次方案覆盖：
1. 基于现有代码的上下文改造路径（不推翻现有业务接口）。
2. 与后续数据持久化（会话、消息、工具审计）的对接方式。
3. 分阶段实施顺序、验收标准与风险控制。

不在本次范围：
- 一次性引入复杂向量召回链路（先关键词检索，再按收益演进）。
- 一次性重构全部 Agent 实现细节（先主链路，再分支链路）。

---

## 2. 当前代码现状（落地前基线）

## 2.1 对话主链路
- 控制器入口：`ParallelLifeController`
- 应用编排：`ParallelLifeApp`
- 上下文方式：`MessageChatMemoryAdvisor + FileBasedChatMemory(kryo)`

现状问题：
1. 会话上下文依赖本地文件，缺乏数据库级可治理能力。
2. `createSession/getSession` 仍偏占位，无法形成会话管理闭环。
3. 难以支撑热/温/冷分层记忆和后续高并发治理。

## 2.2 Agent 链路
- `BaseAgent` 内部通过 `messageList` 维护运行态消息。
- `ToolCallAgent`、`ReActAgent` 在执行时同样依赖内存消息列表。

现状问题：
1. 与主链路记忆体系并存，策略不统一。
2. 缺少会话后沉淀与自愈流程。

## 2.3 持久化基线
当前尚未接入 Repository/Mapper/Flyway 主链路，已完成数据库表结构前置设计文档：
- `chat_session`
- `chat_message`
- `tool_call_audit`
- 预留：`memory_topic_index`

---

## 3. 目标架构（代码层）

## 3.1 设计原则
1. 先保证现有接口兼容，再替换底层记忆实现。
2. 先打通数据库最小闭环，再增加三层记忆与自愈。
3. 请求主链路仅做必要加载，沉淀与治理异步化。
4. 统一异常语义：`BusinessException + ErrorCode`。

## 3.2 模块职责拆分（建议新增）
- `context/`
  - `ContextManager`：上下文总入口（构建/回写）。
  - `ContextAssembler`：在预算内拼装最终上下文包。
  - `TopicSelector`：温层 topic 选择器。
  - `ContextBudgetPolicy`：token/字节预算与降级策略。
- `memory/`
  - `HotMemoryProvider`：读取热层规则与索引。
  - `WarmMemoryService`：温层 topic 管理与评分。
  - `ColdMemoryService`：冷层检索与压缩注入。
  - `MemoryHealer`：会话后自愈任务（提炼/去重/降级/淘汰）。
- `session/`
  - `ChatSessionService`：会话创建/查询/状态变更。
  - `ChatMessageService`：消息追加/查询最近 N 条/关键词检索。
- `audit/`
  - `ToolAuditService`：工具调用审计写入。

## 4. 三层记忆与数据库映射

## 4.1 热层（Hot）
来源：
- `MEMORY.md`（项目规则、模块索引、高风险提醒）。

落地建议：
1. 保留文件形态作为权威输入。
2. 增加短 TTL 本地缓存，降低频繁 IO。
3. 请求前固定加载，不参与激进压缩。

## 4.2 温层（Warm）
来源：
- 结构化索引建议落在 `memory_topic_index`。
- topic 正文可先文件化，后续再数据库化。

落地建议：
1. 先实现“索引在表、正文在文件”的混合模式，降低首期复杂度。
2. `TopicSelector` 使用“相关度 + priority + quality_score + ttl_days”打分取 Top-N。
3. 请求超时或预算不足时，允许降级为仅加载高优先级 topic。

## 4.3 冷层（Cold）
来源：
- `chat_message` 作为原始证据层（先不额外引入 raw jsonl 双写）。

落地建议：
1. 默认不加载，出现信息缺口时再检索。
2. 先关键词检索（chatId + 时间窗 + term），结果二次摘要后注入。
3. 严格限制注入条数与字节大小，防止污染当前推理。

## 5. 与现有代码的具体改造点

## 5.1 `ParallelLifeController`
改造点：
1. `createSession()` 从“生成 UUID 返回”升级为 `chat_session` 落库。
2. `getSession()` 从示例返回升级为真实查询。
3. 对话接口入参保持不变，内部改由服务层处理上下文读取与消息回写。

## 5.2 `ParallelLifeApp`（第一优先）
当前该类直接依赖 `MessageChatMemoryAdvisor`。

目标改造：
1. 请求前调用 `ContextManager.buildContext(request)`。
2. LLM 调用使用组装后的上下文包。
3. 请求后调用 `ContextManager.afterRun(result)` 异步沉淀。

兼容策略：
- 通过配置开关控制“旧记忆（kryo）/新记忆（DB+三层）”，平滑切换。

## 5.3 `BaseAgent` / `ToolCallAgent`
改造策略：
1. 保留 `messageList` 作为运行态临时状态，避免一次性重写。
2. 启动时先注入 `ContextManager` 构建的上下文片段。
3. 结束后将关键结果沉淀到 `chat_message` 与温层候选。

## 6. 分阶段实施计划（可执行）

## Phase 1：数据持久化最小闭环（P0）
目标定义：会话与消息数据库闭环可用。

改动范围：
1. 接入持久化依赖与迁移能力（建议 Flyway）。
2. 落地 `chat_session`、`chat_message`、`tool_call_audit` 基础表。
3. 新增 `ChatSessionService`、`ChatMessageService`，替换控制器占位逻辑。

验证方式：
1. 创建会话成功并可查询。
2. 对话后用户/助手消息可落库并按时间或序号恢复。
3. 工具调用失败时有 `tool_call_audit` 记录。

下一步：
- 进入 `ContextManager` 接管请求前后流程。

## Phase 2：上下文读取链路切换（P0/P1）
目标定义：主链路由 `ContextManager` 统一构建上下文。

改动范围：
1. 新增 `ContextManager`、`ContextAssembler`、`ContextBudgetPolicy`。
2. `ParallelLifeApp` 三类对话（普通/RAG/工具）统一接入。
3. 保留降级路径：构建失败时回退“最近消息 + 当前输入”。

验证方式：
1. 长对话下响应稳定，无明显上下文丢失。
2. token 用量相对旧链路有下降趋势。
3. 无破坏现有接口协议。

下一步：
- 增加温层 topic 选择与冷层关键词兜底。

## Phase 3：温层与自愈（P1）
目标定义：实现经验沉淀、质量评分与生命周期治理。

改动范围：
1. 接入 `memory_topic_index`（或等价结构）。
2. 实现 `TopicSelector`（Top-N + 预算截断）。
3. 实现 `MemoryHealer` 异步任务：提炼、去重、降级、淘汰。

验证方式：
1. 热门场景 topic 命中率上升。
2. 低质量内容可自动降级，过期内容可治理。
3. 请求主链路时延不因自愈任务显著上升。

下一步：
- 进入压缩管线与并发优化。

## Phase 4：压缩与并发治理（P1/P2）
目标定义：在高并发与长会话下控制成本与稳定性。

改动范围：
1. 落地 Snip/Collapse/Reactive 三个核心压缩动作（先不全量五级）。
2. 冷层检索设置超时，超时自动降级。
3. 会话后任务异步队列化，避免阻塞主请求。

验证方式：
1. 上下文平均 token 下降。
2. P95 时延改善或持平。
3. 压缩失败可回退最小上下文模板。

## 7. 关键接口建议（示例）

```java
public interface ContextManager {
    ContextPackage buildContext(ContextBuildRequest request);
    void afterRun(ContextRunResult result);
}

public interface ChatSessionService {
    String createSession(String userId, String sessionName);
    SessionDTO getByChatId(String chatId);
}

public interface ChatMessageService {
    void appendUserMessage(String chatId, String content, String metadataJson);
    void appendAssistantMessage(String chatId, String content, String metadataJson);
    List<MessageDTO> listRecent(String chatId, int limit);
}
```

---

## 8. 异常与降级策略（统一语义）
1. 参数与前置校验失败：直接抛 `BusinessException(ErrorCode.BAD_REQUEST/VALIDATION_FAILED)`。
2. 上下文构建失败：记录日志并降级，不中断主流程。
3. 持久化失败：
   - 主消息写入失败可按“重试 + 告警”处理；
   - 自愈与审计失败不影响主请求，但必须留审计日志。
4. 禁止多层冗余 try-catch；在必要边界做单点异常转换。

---

## 9. 首批验收指标（建议）
1. 会话与消息 DB 化后，能稳定恢复最近 N 轮上下文。
2. 平均上下文 token 较旧链路下降（建议目标 20%~30%）。
3. 对话主流程成功率不下降，工具调用审计可追溯。
4. 上下文构建超时时可自动降级并保持服务可用。

---

## 10. 结论
本方案建议采用“先主链路、后治理层”的渐进改造：
1. 先用数据库打牢会话与消息地基；
2. 再由 `ContextManager` 统一三层记忆入口；
3. 最后引入自愈与压缩体系。

这样可在不破坏现有接口的前提下，把当前内存/文件型上下文升级为可治理、可扩展、可审计的工程化上下文系统。

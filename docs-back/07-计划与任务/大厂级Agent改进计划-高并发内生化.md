# 大厂级 Agent 改进计划（高并发内生化）

## 1. 背景与目标
当前项目已经具备一定的 Agent 功能雏形。接下来需要把它从“能跑的 Agent”升级为“可运营的 Agent 平台”，达到大厂级别的稳定性、可观测性、安全性与工程治理能力。

本计划重点目标：
1. **平台化升级**：将编排、模型接入、工具执行、记忆/RAG、鉴权与审计等能力进行层次化与产品化，使其可扩展、可替换、可演进。
2. **高并发内生化**：把并发治理作为系统一等公民，覆盖连接、会话、编排执行、工具调用、检索与模型请求的全链路，并提供背压、限流、取消、隔离与降级机制。
3. **可评测可回归**：引入离线评测与在线灰度，使每次 Prompt/检索/工具策略变化都能验证质量与成本。
4. **可观测可追责**：通过全链路 Trace/Metric/Log 让每次 Agent 行为可定位、可复盘、可审计。

非目标（先不做，避免分散精力）：
- 不追求一次性实现“单体全能 Agent”，而是先把平台骨架与治理能力打牢。
- 不在本阶段对业务侧能力做大规模堆功能，更多聚焦并发与工程化能力。

---

## 2. 总体改造思路
把系统从“业务调用 Agent”改为“Agent 平台编排执行”：
1. **入口层（API/BFF）**：鉴权、限流、租户隔离、统一流式输出（SSE/WebSocket）、任务化入口。
2. **编排层（Orchestrator）**：负责会话状态、计划生成、工具路由、并行分支、重试/超时/取消、DAG 执行与回放能力。
3. **工具执行层（Tool Runtime）**：工具注册、权限校验、隔离舱（bulkhead）、并发上限、熔断/降级、可观测。
4. **模型接入层（Model Gateway）**：统一路由与降级、多模型管理、缓存、并发与成本治理。
5. **记忆与 RAG 层**：短期/长期记忆分层、检索并行、召回融合、权限裁剪、缓存与一致性策略。
6. **评测与观测层**：Trace/Metric/Log、离线 golden set、在线灰度与自动回归。

并发治理原则：
- **异步化**：把耗时链路从请求线程中剥离（任务队列 + 流式进度）。
- **受控并发**：用“每一类资源的并发上限 + 队列 + 超时”控制系统行为，而不是无上限并发。
- **背压与降级**：下游慢就降级（更少检索、更小模型、更少工具、更激进缓存）而不是无限等待或崩溃。
- **取消传播**：用户取消时能停止模型与工具调用，释放资源。
- **隔离**：租户/工具/外部依赖之间互不拖垮（舱壁隔离）。

## 3. 高并发内生化方案（核心章节）
### 3.1 连接与会话：从同步阻塞到“流式 + 可取消 + 背压”
1. **统一流式输出**：SSE 或 WebSocket 传递 token 增量、检索进度、工具执行状态，避免长轮询导致线程/连接耗尽。
2. **可取消**：为每次推理/任务保留 `requestId/taskId`，在用户停止时触发取消信号：
   - 模型流式生成停止
   - 工具执行停止或跳过
   - 编排层结束并做资源回收
3. **背压与排队**：
   - 入口层限制连接/并发会话数
   - 下游排队长度达到阈值时触发快速失败或降级策略

### 3.2 编排执行：并行化但必须“受控”
编排层引入受控并行能力（并发不是越大越好）：
1. **DAG 并行**：把可并行的子任务并行执行，例如：
   - 多路检索（关键词检索 + 向量检索 + 结构化库）
   - 多工具竞速（取最先可用结果或取聚合结果）
2. **并发额度**：对每个维度设置额度：
   - 每个会话并发分支数上限
   - 每个租户并发额度
   - 每个外部依赖并发上限（例如某个 HTTP 工具）
3. **超时与重试**：区分可重试与不可重试错误，避免放大故障。

### 3.3 系统级限流与隔离：四层治理模型
建议采用“四层限流 + 隔离舱”：
1. **入口限流**：API 层 QPS、连接数、突发策略（token bucket/leaky bucket）。
2. **租户限流**：租户级配额与优先级队列，保证大客户不会被小客户拖垮。
3. **资源限流**：
   - 模型并发
   - 向量库/检索并发
   - 工具执行并发
4. **成本限流**：token/s、日预算、峰值告警；超过阈值自动降级（更小模型、减少检索深度）。

隔离舱（bulkhead）策略：
- 某个工具或某个依赖失败，只影响该工具链路；不影响其他链路。
- 对不可控外部依赖使用“熔断 + 快速失败 + 缓存兜底”。

### 3.4 缓存策略：在高并发下用缓存换稳定性
缓存应当“带权限、带租户、带一致性策略”：
1. **检索缓存**：同一用户/租户在相同 query 与相同权限上下文下的召回结果缓存。
2. **嵌入与向量检索缓存**：热点 chunk 的 embedding 或召回结果缓存（注意更新策略）。
3. **工具结果缓存（可选）**：对幂等、只读工具（例如查询类接口）可以缓存；写操作禁止缓存。
4. **Prompt/模板缓存**：减少 Prompt 拼接开销与模板错误。

## 4. 工程化能力建设（让平台可持续演进）
### 4.1 状态与一致性：外置会话状态 + 幂等与去重
高并发场景下，必须避免“多实例时状态不一致”：
1. 会话状态外置（例如通过持久化存储/缓存存储）。
2. 工具调用与任务执行提供幂等键：
   - `idempotencyKey` 用于去重
   - 对重试链路避免重复写操作
3. 编排层支持回放（replay）能力，便于定位线上问题。

### 4.2 工具平台化：注册中心 + 权限校验 + 隔离与观测
把工具从“方法调用”升级为“受治理的能力”：
1. 工具注册中心：声明输入输出 schema、权限要求、超时、重试策略、成本权重。
2. 工具执行运行时：
   - 权限校验（租户 + 用户 + 工具级 ACL）
   - 超时控制
   - 隔离（并发额度、熔断、降级）
3. 工具级别观测指标：成功率、P95 延迟、超时率、熔断次数。

### 4.3 评测与回归：把“质量”变成可量化
1. 离线评测（golden set）：
   - 场景覆盖：问答、检索命中、工具调用、拒答/安全策略
   - 指标：准确率、引用率、不可回答率、工具误调用率、成本指标
2. 在线灰度：
   - Prompt 版本灰度
   - 检索参数策略灰度
   - 失败与成本阈值自动回滚
3. 自动回归：
   - 每次改动后触发对比评测
   - 输出可读报告便于团队迭代

## 5. 安全与合规（高并发下更容易出问题）
建议最小化风险的安全策略：
1. 租户隔离：所有数据访问、索引查询、缓存 key 必须携带租户上下文。
2. 权限裁剪：检索阶段就裁剪权限，避免“先检索后过滤”泄露风险。
3. 脱敏与审计：
   - 日志/Trace 进行 PII 脱敏
   - 工具调用记录审计（尤其写操作工具）
4. 速率限制与配额：防止恶意用户或异常脚本打爆系统。

---

## 6. 可观测与运维（大厂级别必须做）
### 6.1 全链路 Trace
每次 Agent 请求贯穿以下环节，并可通过 `traceId/requestId` 串起来：
- API 入口
- 编排层决策与状态变化
- 检索（多路检索/融合）
- 模型调用（路由、token、耗时）
- 工具执行（入参摘要、耗时、结果状态）

### 6.2 核心指标（建议口径固定）
1. 吞吐：RPS、并发会话数、队列长度。
2. 时延：端到端 P50/P95/P99，分别统计模型、检索、工具耗时。
3. 成功率：成功率、失败率、超时率、重试率、取消率。
4. 成本：token 成本、工具成本、缓存命中率。
5. 稳定性：熔断次数、降级次数、异常分布。

## 7. 里程碑路线图（建议 4 阶段）
### Phase A：平台骨架（1-2 周）
- 编排层抽象与统一接口（会话、计划、工具路由）
- 模型接入统一网关（路由、缓存、降级接口）
- 工具注册与执行规范（schema、超时、权限）
- 全链路 traceId 贯通

### Phase B：高并发内核（1-2 周）
- SSE/WebSocket 流式输出与可取消
- 受控并行（DAG 并行 + 分支并发额度）
- 四层限流 + bulkhead 隔离
- 背压策略（排队、超时、快速失败、降级）
- 检索与工具缓存落地（带权限）

### Phase C：质量与治理（持续迭代）
- golden set 离线评测
- 在线灰度与自动回归
- 成本治理（预算阈值 + 降级策略联动）

### Phase D：企业级能力（持续迭代）
- 多租户增强（配额、优先级、审计）
- 更细粒度权限模型
- SLA/运维面板与告警体系

## 9. 我建议的“最关键抓手”（先做对，再谈细节）
如果要在现阶段优先级最高的抓手，我建议是：
1. **编排层产品化**：让所有 Agent 行为都经过编排层，才能统一并发治理、取消与回放。
2. **可控并行 + 限流隔离**：没有隔离与额度的并行会放大故障；先把“并发行为”治理好。
3. **可观测闭环 + 离线评测**：没有数据，优化只能靠感觉；闭环才能持续变强。

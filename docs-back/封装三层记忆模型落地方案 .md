## 生产级核心规则（必须严格执行）
1. **单向流动铁则**：数据只能从 `冷记忆 → 温记忆 → 热记忆` 单向流动，绝对禁止反向写入，从根源避免数据污染
2. **先写原则**：任何交互产生的原始数据，必须先写入冷记忆落盘，再执行上层记忆更新，保证数据零丢失
3. **异步解耦**：所有提炼、索引更新、更早轮次压缩摘要操作全部在后台异步执行，绝对不阻塞用户的实时对话响应
4. **召回优先级**：严格遵循 `热记忆（必加载）> 温记忆（用户专属）> RAG（通用知识）> 冷·当前会话（必加载，滑动窗口）> 冷·跨会话（特殊场景）`
5. **冷记忆红线（双轨）**：
    - **当前会话**：允许完整记录或滑动窗口压缩结果直接进入上下文；多轮连贯性由冷层负责，热层不存最近轮次摘要
    - **跨会话归档**：禁止大段原始数据直接灌入上下文，必须先摘要/提炼后再使用
6. **容量硬限制**：
    - 热记忆：≤1MB（全局+会话总和）
    - 温记忆：单用户最多100个知识块，单块≤50KB
    - 单次召回：温记忆Top5 + RAG Top3，总Token≤2000
    - 冷·当前会话入上下文：最近3轮全文 + 更早摘要总长有硬预算（见冷记忆章节）

## 二、融合版三层记忆详细设计（1:1可落地）
### （一）热记忆：核心配置+全局索引（必加载、极致快）
**融合定位**：保留原方案“身份锚点+会话工作记忆”的生产级规则，融入新架构“全局索引目录”的效用逻辑，既保证每次对话的核心规则刚性，又解决温记忆检索泛化问题。会话运行时仅保留任务进度与待办，**多轮对话连贯性改由冷·当前会话滑动窗口承担**，不再在热层存放最近N轮交互摘要。

#### 1. 存储结构（双轨制+索引化）
| 分类 | 用户全局核心锚点（跨会话） | 全局索引目录（跨会话） | 会话运行时状态（单会话） |
| --- | --- | --- | --- |
| 核心内容 | 1. 垂直领域核心边界/身份   2. 用户刚性偏好/禁忌   3. 系统安全规则（原） | 1. 文档索引（名称/ID/摘要/标签）   2. 项目索引（名称/ID/状态）   3. 温记忆索引（知识块分类/检索入口）   4. 技能索引（名称/适用场景）（新） | 1. 当前会话任务进度   2. 待办事项（≤10条）（原+新）   ❌ 不存最近N轮交互摘要/对话原文（多轮连贯性由冷·当前会话负责） |
| 容量限制 | ≤5KB/50行（原） | ≤500KB（索引轻量化） | ≤25KB/200行（原） |
| 存储形式 | Redis String（原） | Redis Hash（索引键值对） | Redis List（原） |
| 访问规则 | 100%加载到Prompt最顶部 | 每次对话加载，用于快速定位温记忆/RAG内容 | 会话内实时更新，LTRIM自动截断；不承担多轮对话原文/摘要 |


#### 2. 生产级规则（原+新）
+ 原子操作：追加内容时先截断再写入，超限自动追加WARNING（原）；
+ 索引实时更新：温记忆/文档新增/修改时，异步更新热记忆中的全局索引（新）；
+ 持久化兜底：Redis热记忆每5分钟同步到SQLite，避免内存丢失（新）。

### （二）温记忆：结构化知识库+RAG联动（高价值、可检索）
**融合定位**：摒弃原方案“温记忆=泛化经验”的模糊性，锚定新架构“结构化知识”核心，同时保留原方案RAG深度联动能力，形成“用户专属知识（温记忆）+ 通用专业知识（RAG）”的双层知识体系。

#### 1. 存储内容（结构化+场景化）
| 知识类型 | 来源（原+新） | 存储形式 | 核心规则 |
| --- | --- | --- | --- |
| 用户专属规则 | 原温记忆（偏好/踩坑记录/禁忌） | PostgreSQL JSONB（结构化元信息）+ Markdown（内容） | 优先级高于RAG，仅存个性化内容 |
| 项目经验库 | 新架构（目标/技术栈/问题/方案） | 同上 + pgvector向量（语义检索） | 单项目1条摘要，≤500字 |
| 对话摘要库 | 新架构（主题/需求/共识/待办） | 同上 | 单会话1条摘要，异步生成 |
| 技能知识库 | 新架构（步骤/示例/注意事项） | 同上 | 按技能分类，支持关键词+语义检索 |


#### 2. 生产级联动规则（原+新）
+ 检索逻辑：先通过热记忆全局索引定位温记忆分类 → 再执行“关键词匹配（优先）+ 语义检索（补充）” → 最后召回RAG通用知识（原）；
+ 提炼闭环：冷记忆原始数据异步提炼为温记忆知识块 → 访问频率Top10的知识块更新到热记忆索引（新）；
+ 优先级：温记忆用户规则 > 温记忆结构化知识 > RAG通用知识（原）。

### （三）冷记忆：原始数据仓库 + 当前会话滑动窗口（全量、低成本）
**融合定位**：保留原方案“全量对话落盘、生命周期管理”的生产级能力，扩展新架构“原始文档/系统日志”存储；同时承担**当前对话框多轮连贯上下文**的必返回职责。存储仍是唯一源头；入 Prompt 时拆为双轨。

#### 1. 存储内容（全量+原始）
| 数据类型 | 来源（原+新） | 存储介质 | 生命周期规则 |
| --- | --- | --- | --- |
| 原始对话记录 | 原冷记忆（query/answer/tool_calls/rag_calls） | MySQL（近7天）+ MinIO（超7天） | 按月分区，3个月归档到MinIO，1年可自动删除（原）；**全文永久保留于冷层，压缩只影响入上下文视图** |
| 当前会话更早轮次压缩摘要 | 第4轮起异步生成（主题/决策/待办/关键约束） | MySQL（随会话，可缓存 Redis） | 随会话更新；读取时优先用缓存，缺失则降级为截断/即时压缩 |
| 原始文档 | 新架构（PDF/Word/代码文件） | MinIO | 永久存储，支持版本控制 |
| 系统日志 | 新架构（运行日志/错误日志/性能数据） | ClickHouse | 6个月归档，用于审计/调试 |

#### 2. 双轨职责
| 轨道 | 何时加载 | 入上下文规则 |
| --- | --- | --- |
| 冷·当前会话上下文 | 每次对话**必返回**（与热、温一并返回） | ≤3 轮：返回该对话框全部完整记录；>3 轮：更早轮次压缩摘要 + 最近 3 轮全文 |
| 冷·跨会话归档 | 特殊场景按需（历史回溯、错误复盘、温/RAG 无结果且用户确认） | 禁止大段原文直灌，须先摘要/提炼后再入上下文 |

#### 3. 当前会话返回策略（滑动窗口）
+ **轮次定义**：1 轮 = 1 次 user 消息 + 对应 assistant 回复（含该轮 tool_calls 等原始字段）。
+ **窗口阈值**：最近全文窗口固定为 **3 轮**。
+ **算法**：
  1. 读取当前 `chatId`/`session_id` 下已落盘的完整轮次列表（先写原则：存储侧始终是全文）。
  2. 若轮次数 `N ≤ 3`：原样返回全部完整记录。
  3. 若 `N > 3`：返回 `compress(turns[1..N-3])` + `full(turns[N-2..N])`（即最近 3 轮全文，更早部分用压缩摘要）。
+ **压缩产出字段（更早轮次）**：主题、已确认决策、待办、关键约束/禁忌、关键实体与数字；不保留寒暄与重复过程。
+ **压缩时机**：自第 4 轮起异步生成/增量更新更早摘要缓存；下次请求优先读缓存。缓存未就绪时，可用轻量截断或同步短压缩兜底，避免阻塞主链路。
+ **与热记忆边界**：热记忆会话运行时只保留任务进度与待办，**不存最近 N 轮交互摘要**；多轮连贯性全部由本策略承担。

#### 4. 入上下文 Token 预算（冷·当前会话）
+ 最近 3 轮全文：按实计入，单轮超长时对该轮正文做硬截断并保留首尾。
+ 更早轮次压缩摘要：合计建议 ≤800～1200 Token（可按模型窗口调参），超限则保留最新决策与关键约束，裁剪过程性描述。
+ 跨会话冷召回：单独预算，且必须先摘要；不得与当前会话窗口预算混用导致超限。

#### 5. 生产级规则（原+新）
+ 先写原则：对话结束后先落盘冷记忆全文，再更新热/温记忆（原）；压缩视图不得替代原文存储。
+ 单向流动：冷记忆仅可提炼为温记忆，禁止反向写入（新）。
+ 当前会话必返回：Memory Manager 每次组装上下文时必须包含冷·当前会话滑动窗口结果，与热、温一并返回；热/温召回逻辑不变。
+ 主动遗忘：超3年未访问的原始数据，按用户设置自动删除/归档（新）。
+ 合规留痕：支持数据导出/一键删除，满足等保2.0/GDPR（原）。

## 四、生产级工程化增强（多租户+RAG+熔断）
### （一）多租户/会话隔离（原方案复用）
1. 租户隔离：所有表强制带`user_id`，PostgreSQL开启RLS行级安全，Redis Key前缀加`{tenant_id}`；
2. 会话隔离：会话专属热/温记忆仅当前`session_id`可读写，结束后自动归档；
3. 无痕模式：标记`is_private`的会话，冷记忆不参与提炼，7天后自动清理。

### （二）RAG与温记忆深度联动（融合版）
| 联动模式 | 核心逻辑（原+新） |
| --- | --- |
| 基础模式：索引引导检索 | 先通过热记忆全局索引确定检索范围（如“租赁合同审核”）→ 温记忆召回用户偏好 → RAG召回该场景下的通用法律知识 |
| 进阶模式：知识反哺迭代 | 从RAG调用记录中提炼用户高频查询的知识点 → 生成技能知识库存入温记忆 → 更新热记忆索引 |
| 企业模式：权限过滤 | 温记忆中的用户权限标签 → 过滤RAG检索范围，避免越权内容（原） |


### （三）熔断与容量控制（原方案复用+新适配）
1. 热记忆：行数+字节双限制，超限自动截断（原）；
2. 温记忆：单用户最多100个知识块，单块≤50KB，召回Top5（原）；
3. 冷记忆存储：存储配额硬限制，超限触发清理/扩容提醒（原）；
4. 冷·当前会话入上下文：最近3轮全文 + 更早摘要合计预算（建议更早摘要≤800～1200 Token）；超限优先保留决策与关键约束（新）；
5. 提炼熔断：连续3次提炼失败，停止异步任务并告警，避免无效Token消耗（原）。

### 2. 热记忆管理（索引化+持久化）
```javascript
// 新：更新热记忆全局索引
async function updateHotIndex(userId, indexType, indexKey, indexValue) {
  // 1. 写入Redis Hash（实时访问）
  const indexKeyRedis = `agent:hot:index:${userId}`;
  await redis.hset(indexKeyRedis, `${indexType}:${indexKey}`, indexValue);
  
  // 2. 同步到SQLite（持久化兜底）
  const stmt = sqliteDb.prepare(`REPLACE INTO hot_index 
    (user_id, index_type, index_key, index_value) 
    VALUES (?, ?, ?, ?)`);
  await promisify(stmt.run).bind(stmt)(userId, indexType, indexKey, indexValue);
  
  // 3. 容量校验
  const indexSize = await redis.memory('usage', indexKeyRedis);
  if (indexSize > HOT_INDEX_MAX_SIZE) {
    // 淘汰最久未更新的索引
    const allIndexes = await redis.hgetall(indexKeyRedis);
    const sortedKeys = Object.keys(allIndexes).sort((a, b) => {
      // 简化：按key长度模拟更新时间，实际可存储更新时间戳
      return a.length - b.length;
    });
    await redis.hdel(indexKeyRedis, sortedKeys[0]);
  }
  return true;
}

// 原：更新会话热记忆 + 新：同步SQLite
async function updateSessionHotMemory(sessionId, userId, newSummary) {
  const key = `agent:hot:session:${sessionId}`;
  const entry = `[${new Date().toISOString()}] ${newSummary}`;
  
  // 原子操作（原）
  await redis.multi()
    .lpush(key, entry)
    .ltrim(key, 0, HOT_SESSION_MAX_LINES - 1)
    .expire(key, 86400 * 30)
    .exec();

  // 容量校验（原）
  const memorySize = await redis.memory('usage', key);
  if (memorySize > HOT_GLOBAL_MAX_BYTES) {
    await redis.rpop(key);
    await redis.rpush(key, `> WARNING: MEMORY truncated due to size limits.`);
  }

  // 新：同步到SQLite
  const sessionMemory = await redis.lrange(key, 0, -1);
  sqliteDb.run(`REPLACE INTO hot_session (session_id, user_id, content) VALUES (?, ?, ?)`,
    sessionId, userId, sessionMemory.join('\n'));
  
  return true;
}
```

```javascript
// 从冷记忆提炼温记忆结构化知识
async function extractColdToWarm(userId, sessionId) {
  // 1. 读取冷记忆原始数据（原）
  const [coldRes] = await mysqlPool.execute(`
    SELECT query, answer, tool_calls, rag_calls 
    FROM cold_memory_transcripts 
    WHERE user_id = ? AND session_id = ?
  `, [userId, sessionId]);
  if (coldRes.length === 0) return false;

  // 2. LLM提炼结构化知识（新）
  const rawText = coldRes.map(item => `Q: ${item.query}\nA: ${item.answer}`).join('\n');
  const extractPrompt = `
    从以下原始对话中提炼结构化知识块，仅保留用户个性化内容（偏好/规则/经验），格式为：
    {
      "topic_name": "场景名称",
      "content": "核心规则（Markdown）",
      "tags": ["标签1", "标签2"],
      "scene": "适用场景"
    }
  `;
  const extractRes = await openai.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [{ role: 'user', content: `${extractPrompt}\n【原始对话】\n${rawText}` }]
  });
  const knowledgeBlock = JSON.parse(extractRes.choices[0].message.content);

  // 3. 写入温记忆（原+新）
  const vector = await embeddings.embedQuery(knowledgeBlock.content);
  // 写入PostgreSQL（原）
  await pgPool.query(`
    INSERT INTO warm_memory_topics 
    (user_id, session_id, topic_name, content, frontmatter, content_vector)
    VALUES ($1, $2, $3, $4, $5, $6)
  `, [userId, sessionId, knowledgeBlock.topic_name, knowledgeBlock.content, 
    JSON.stringify({ tags: knowledgeBlock.tags, scene: knowledgeBlock.scene }), 
    `[${vector.join(',')}]`]);
  // 写入Qdrant（新，增强检索）
  await qdrantClient.upsert('warm_memory', {
    points: [{
      id: `${userId}_${knowledgeBlock.topic_name}`,
      vector,
      payload: { user_id: userId, topic_name: knowledgeBlock.topic_name, content: knowledgeBlock.content }
    }]
  });

  // 4. 更新热记忆索引（新）
  await updateHotIndex(userId, 'warm', knowledgeBlock.topic_name, knowledgeBlock.scene);
  return true;
}
```

### 4. 温记忆+RAG联动检索（原+新）
```javascript
async function recallWarmAndRag(userId, sessionId, query) {
  // 1. 从热记忆索引获取检索范围（新）
  const indexKey = `agent:hot:index:${userId}`;
  const warmIndex = await redis.hgetall(indexKey);
  const sceneTags = Object.values(warmIndex).filter(v => v.includes(query)).join(',');

  // 2. 并行召回温记忆+RAG（原）
  const queryVector = await embeddings.embedQuery(query);
  const [warmRes, ragRes] = await Promise.all([
    // 温记忆：带场景过滤（新）
    pgPool.query(`
      SELECT topic_name, content FROM warm_memory_topics
      WHERE user_id = $1 AND is_archived = false
      AND (session_id IS NULL OR session_id = $2)
      AND (frontmatter->>'tags' LIKE $3 OR frontmatter->>'scene' LIKE $3)
      ORDER BY content_vector <-> $4 LIMIT $5
    `, [userId, sessionId, `%${sceneTags}%`, `[${queryVector.join(',')}]`, WARM_TOP_K]),
    // RAG：通用知识（原）
    pgPool.query(`
      SELECT doc_title, doc_chunk FROM rag_knowledge_base
      WHERE is_valid = true
      ORDER BY doc_vector <-> $1 LIMIT $2
    `, [`[${queryVector.join(',')}]`, RAG_TOP_K])
  ]);

  // 3. 结果融合（原）
  const warmContent = warmRes.rows.map(row => `> ${row.topic_name}：${row.content}`).join('\n');
  const ragContent = ragRes.rows.map(row => `> ${row.doc_title}：${row.doc_chunk}`).join('\n');
  return `【用户专属知识】\n${warmContent}\n\n【专业知识库】\n${ragContent}`;
}
```

## 八、核心避坑指南（融合版）
1. 索引轻量化：热记忆索引只存“定位信息”（如场景/标签），不存完整知识，避免膨胀；
2. 提炼单向性：冷记忆仅能提炼为温记忆，禁止温记忆回写冷记忆，避免数据污染；
3. 优先级刚性：温记忆用户规则永远高于RAG，AI可补充RAG知识，但不能推翻用户规则；
4. 异步解耦：所有提炼/索引更新操作异步执行，不阻塞对话主流程；
5. 存储复用：PostgreSQL同时承载温记忆+RAG，避免多组件运维成本（原）。

## 九、适用场景
本融合方案完美适配：

+ 个人助理/开发者助手（需要长期沉淀个性化知识）；
+ 垂直领域Agent（合同审核/考研辅导/客服，需要RAG专业支撑+用户记忆）；
+ 企业内部知识库助手（多租户隔离+集体记忆沉淀）。

该方案既保留了原架构的生产级工程化能力，又融入了新架构的效用驱动逻辑，解决了传统Agent“记忆臃肿、检索泛化、知识无沉淀”的核心痛点，实现“越用越精准、越用越智能”的闭环。

## 十、核心能力：温记忆+RAG深度联动方案
### （一）核心职责边界（绝对不能乱）
| 模块 | 核心存储内容 | 核心定位 | 优先级 |
| :--- | :--- | :--- | :--- |
| **温记忆** | 用户动态、个性化、专属的场景经验、偏好、踩坑记录、专属规则 | 解决「记不住用户、千人一面、重复提问」的问题 | 最高，必须优先遵守 |
| **RAG** | 静态、通用、权威的垂直领域专业知识库、行业规范、官方文档、标准模板 | 解决「大模型幻觉、知识过期、输出不专业」的问题 | 补充，仅用于专业合规性支撑，不能推翻温记忆的用户规则 |


### （二）4种联动模式落地顺序（从基础到进阶）

**执行步骤**：

1. 用户提问向量化/关键词提取
2. 并行执行两条召回链路：

3. 按固定格式融合，温记忆放在前面，明确标注优先级
4. 检查Token总量，超限则轻量化压缩

## 十一、端到端完整业务闭环流程
### （一）对话前置处理流程（用户发起提问后，第一步执行）
1. **权限校验**：校验用户ID、会话ID的合法性，初始化用户记忆环境，新用户自动创建记忆目录
2. **热记忆预加载**：读取用户全局热锚点 + 当前会话专属热记忆（任务进度/待办），确定核心规则与运行时状态
3. **温记忆+RAG并行召回**：执行联动召回逻辑，拿到融合后的个性化规则+专业知识
4. **冷·当前会话必加载**：按滑动窗口返回当前对话框记录（≤3轮全文；>3轮：更早压缩摘要 + 最近3轮全文）；读取时优先用更早摘要缓存
5. **［按需］冷·跨会话检索**：仅特殊场景触发，结果须先摘要/提炼后再并入
6. **上下文压缩校验**：检查总Token量（含冷·当前会话预算），超过阈值时从轻到重触发压缩，带3次失败熔断的断路器机制

### （二）标准Prompt组装流程（固定顺序，不可乱）
```markdown
【系统设定】垂直Agent核心身份与功能边界（固定写死）
【热记忆·用户全局核心规则（必遵守）】
【温记忆·用户专属个性化规则（最高优先级）】
【RAG·专业权威知识库（合规补充）】
【热记忆·当前会话运行时（任务进度/待办，不含多轮对话摘要）】
【冷记忆·当前会话滑动窗口（≤3轮全文；>3轮：更早压缩+最近3轮全文）】
【用户当前提问】
```

### （三）对话写入与记忆迭代流程（LLM返回结果后，原子执行）
1. **冷记忆落盘**：将本轮完整对话（query/answer/tool_calls/rag_calls）写入MySQL冷记忆表，保证数据永久留存（先写原则）
2. **冷·滑动窗口缓存更新**：若当前会话已超过3轮，异步生成/增量更新「更早轮次」压缩摘要缓存，供下次必加载使用
3. **热记忆更新**：仅更新会话任务进度与待办事项到Redis会话专属热记忆，自动执行`LTRIM`截断，遵守200行/25KB硬限制；**不追加多轮对话摘要**
4. **用户状态刷新**：更新MySQL用户表的`last_active_at`，刷新Redis所有key的过期时间
5. **记忆迭代触发**：累计满10轮对话/会话结束/用户给出反馈时，自动触发温记忆提炼，更新用户专属记忆
6. **生命周期管理**：每日定时执行冷记忆压缩归档、不活跃用户记忆归档、温记忆过期淘汰

## 十二、多租户与会话隔离完整方案
1. **租户级隔离**：所有表强制带`user_id`字段，开启数据库行级安全策略（RLS），确保每个用户只能访问自己的记忆数据，从根源杜绝跨用户串扰
2. **会话级隔离**：会话专属热/温记忆，仅当前`session_id`可读写，会话结束后自动归档，不会污染其他会话
3. **无痕模式实现**：标记`is_private=true`的会话，对话日志仅临时存储，不参与记忆提炼，会话结束后立即删除所有会话级记忆，7天后自动清理冷记忆日志
4. **不活跃用户管理**：超过6个月未活跃的用户，Redis热记忆归档到MySQL，释放内存；温记忆全量标记归档；冷记忆全量归档到低成本对象存储，极致控制资源占用

### 2. 热记忆管理模块
```javascript
// 热记忆Key生成
const HOT_GLOBAL_KEY = (userId) => `agent:hot:global:${userId}`;
const HOT_SESSION_KEY = (sessionId) => `agent:hot:session:${sessionId}`;

// 更新会话专属热记忆（带双保险截断）
async function updateSessionHotMemory(sessionId, userId, newSummary) {
  const key = HOT_SESSION_KEY(sessionId);
  const entry = `[${new Date().toISOString()}] ${newSummary}`;
  
  // 原子操作：追加+行数截断
  await redis.multi()
    .lpush(key, entry)
    .ltrim(key, 0, HOT_MEMORY_MAX_LINES - 1)
    .expire(key, 86400 * 30)
    .exec();

  // 字节兜底截断
  const memorySize = await redis.memory('usage', key);
  if (memorySize > HOT_MEMORY_MAX_BYTES) {
    await redis.rpop(key);
    await redis.rpush(key, `> WARNING: MEMORY.md is truncated due to size limits. Only part of it was loaded.`);
  }

  // 刷新用户活跃时间
  await mysqlPool.execute('UPDATE users SET last_active_at = NOW() WHERE user_id = ?', [userId]);
  return true;
}

// 读取热记忆完整内容
async function getHotMemory(userId, sessionId) {
  const [globalMemory, sessionMemory] = await Promise.all([
    redis.get(HOT_GLOBAL_KEY(userId)),
    redis.lrange(HOT_SESSION_KEY(sessionId), 0, -1)
  ]);

  return {
    global: globalMemory || '# 用户全局核心规则\n- 暂无自定义规则',
    session: sessionMemory.join('\n') || '# 当前会话上下文\n- 暂无会话记录'
  };
}
```

### 3. 温记忆+RAG联动召回核心模块
```javascript
// 温记忆+RAG并行召回+融合核心函数
async function recallWarmAndRag(userId, sessionId, query) {
  // 1. 生成提问向量
  const queryVector = await embeddings.embedQuery(query);
  const vectorStr = `[${queryVector.join(',')}]`;

  // 2. 并行执行温记忆召回 + RAG召回
  const [warmRes, ragRes] = await Promise.all([
    // 温记忆召回：仅当前用户的未归档内容
    pgPool.query(
      `SELECT topic_name, content FROM warm_memory_topics
       WHERE user_id = $1 AND is_archived = false
       AND (session_id IS NULL OR session_id = $2)
       ORDER BY content_vector <-> $3
       LIMIT $4`,
      [userId, sessionId, vectorStr, WARM_TOP_K]
    ),
    // RAG召回：有效内容，可加权限过滤
    pgPool.query(
      `SELECT doc_title, doc_chunk FROM rag_knowledge_base
       WHERE is_valid = true
       ORDER BY doc_vector <-> $1
       LIMIT $2`,
      [vectorStr, RAG_TOP_K]
    )
  ]);

  // 3. 结果融合，生成标准Prompt块
  const warmContent = warmRes.rows.length > 0 
    ? `【温记忆·用户专属规则（最高优先级，必须100%遵守）】\n${warmRes.rows.map(row => `> ${row.topic_name}：${row.content}`).join('\n')}`
    : '';

  const ragContent = ragRes.rows.length > 0
    ? `【RAG·专业权威知识库（合规补充）】\n${ragRes.rows.map(row => `> ${row.doc_title}：${row.doc_chunk}`).join('\n')}`
    : '';

  return `${warmContent}\n\n${ragContent}`.trim();
}
```

## 十、核心避坑指南（生产级必看）
1. **绝对禁止边界混乱**：温记忆只存用户个性化内容，RAG只存通用专业知识，绝对不能把RAG的静态知识存到温记忆里，否则会导致温记忆臃肿、知识过期、内容冲突
2. **严格遵守优先级规则**：温记忆的用户规则优先级永远高于RAG，AI可以用RAG补充合规性，但绝对不能推翻用户明确提出的要求
3. **严格控制容量上限**：热记忆严格遵守双限制，温记忆+RAG召回内容不超过上下文Token上限的30%，避免挤占对话空间导致大模型断片
4. **避免过度迭代**：温记忆更新必须有明确的触发条件，不能每轮对话都更新，定期清理超过6个月未访问的归档内容，避免无效内容堆积
5. **熔断机制必加**：上下文压缩、记忆提炼、RAG调用必须加失败熔断，连续失败3次立即停止，避免无效API调用与Token浪费
6. **数据安全必守**：全链路租户隔离，敏感数据脱敏，开启数据库备份，绝对不能出现跨用户数据串扰的低级错误

## 一、温记忆文档生成的核心铁则（先定边界，绝对不能破）
温记忆的核心定位是**用户专属的动态经验库**，不是通用知识库，生成全程必须遵守以下铁则，从根源避免记忆污染、冗余、失效：

1. **只存个性化内容，不存通用知识**：绝对不把RAG里的行业规范、官方文档、通用模板存入温记忆，只存和这个用户强相关的偏好、规则、踩坑记录、专属约定。
2. **场景化拆分，不搞大杂烩**：一个话题文档只对应一个垂直细分场景，比如「租赁合同审核偏好」「SQL编写规范」，绝不把所有内容塞到一个大文件里，保证召回精准度。
3. **以最新状态为准，自动解决冲突**：同一个规则出现矛盾时，永远以用户最新的表述为准，自动覆盖旧规则，不保留过时、冲突的内容。
4. **只存可执行的规则，不存流水账**：只存能改变AI输出行为的内容，比如「用户要求合同必须约定原告所在地法院」，不存「2026-04-20用户审核了一份合同」这种无意义的流水账。
5. **严格控制单文档体积**：单篇温记忆文档内容控制在50KB以内，最多不超过100行，保证召回后不占用过多Token，不挤占对话上下文。

### 阶段二：对话中自动生成与迭代（核心闭环，实现越用越好用）
这是温记忆文档生成的核心环节，复刻Claude Code的Auto Memory自动记忆机制，**全程异步执行，不影响用户实时对话体验**，自动完成「新文档创建→已有文档更新→过时文档归档」全流程。

#### 1. 明确触发时机（不是每轮对话都生成，避免无效更新）
只有满足以下条件，才触发温记忆文档的生成/更新，避免记忆臃肿：

| 触发类型 | 具体触发条件 |
| :--- | :--- |
| 强触发（必执行） | 1. 用户明确纠正AI的错误：「不对，应该是XX」「以后别再XX」   2. 用户明确提出长期规则：「记住，以后所有内容都要XX」   3. 用户对同一个问题连续纠正2次及以上   4. 单会话任务结束，用户明确给出「完成/满意」反馈 |
| 弱触发（可选执行） | 1. 单会话累计满10轮对话   2. 同一个RAG知识点用户连续查询3次及以上   3. 用户新开会话，重复提起上一个会话的相同需求 |
| 禁止触发 | 1. 单次闲聊、无意义对话   2. 一次性临时需求，无长期复用价值   3. 纯通用知识问答，无用户个性化内容 |


#### 2. 自动生成/更新全流程
```plain
用户对话结束 → 写入冷记忆落盘 → 异步触发记忆提炼
        ↓
判断是否符合触发条件 → 不符合则直接终止
        ↓
符合条件 → 调用LLM分析本轮对话，提取可记忆内容
        ↓
判断内容归属：已有话题？新话题？过时内容？
        ├─ 已有话题 → 执行「文档更新逻辑」，合并新规则，解决冲突，更新元信息
        ├─ 新话题 → 执行「新文档创建逻辑」，按标准化结构生成新文档，写入数据库
        └─ 过时内容 → 执行「文档归档逻辑」，标记is_archived=true，不再参与召回
        ↓
更新话题向量，完成记忆迭代闭环
```

#### 4. 可直接复用的代码实现（Node.js，兼容之前的架构）
```javascript
/**
 * 异步处理温记忆文档的自动生成与更新
 * @param {string} userId 用户ID
 * @param {string} sessionId 会话ID
 * @param {object} conversation 本轮对话内容 {query, answer, feedback}
 */
async function autoUpdateWarmMemory(userId, sessionId, conversation) {
  const { query, answer, feedback } = conversation;

  // 1. 先获取用户已有温记忆话题列表
  const topicsRes = await pgPool.query(
    `SELECT topic_name FROM warm_memory_topics WHERE user_id = $1 AND is_archived = false`,
    [userId]
  );
  const existTopics = topicsRes.rows.map(row => row.topic_name);

  // 2. 调用LLM提取有效记忆内容，判断操作类型
  const extractRes = await llmClient.chat.completions.create({
    model: 'gpt-4o-mini',
    temperature: 0.1,
    response_format: { type: 'json_object' },
    messages: [
      { role: 'system', content: 记忆提取与分类Prompt },
      { role: 'user', content: JSON.stringify({
        user_id: userId,
        本轮对话: { query, answer, feedback },
        已有温记忆话题列表: existTopics
      })}
    ]
  });
  const memoryResult = JSON.parse(extractRes.choices[0].message.content);

  // 3. 无有效记忆，直接终止
  if (!memoryResult.has_valid_memory || memoryResult.action === 'ignore') {
    return false;
  }

  // 4. 处理更新已有话题
  if (memoryResult.action === 'update') {
    const targetTopic = memoryResult.target_topic;
    // 读取已有文档内容
    const docRes = await pgPool.query(
      `SELECT content, frontmatter FROM warm_memory_topics WHERE user_id = $1 AND topic_name = $2`,
      [userId, targetTopic]
    );
    const { content: oldContent, frontmatter: oldFrontmatter } = docRes.rows[0];

    // 调用LLM更新文档
    const updatedDoc = await llmClient.chat.completions.create({
      model: 'gpt-4o-mini',
      temperature: 0.1,
      messages: [
        { role: 'system', content: 温记忆文档更新Prompt },
        { role: 'user', content: JSON.stringify({
          操作类型: 'update',
          已有文档内容: oldContent,
          新增记忆内容: memoryResult.memory_content
        })}
      ]
    });
    const newContent = updatedDoc.choices[0].message.content;

    // 重新生成向量，更新数据库
    const contentVector = await embeddings.embedQuery(newContent);
    await pgPool.query(
      `UPDATE warm_memory_topics
       SET content = $1, content_vector = $2, frontmatter = jsonb_set(frontmatter, '{updated_at}', $3), updated_at = NOW(), last_accessed_at = NOW()
       WHERE user_id = $4 AND topic_name = $5`,
      [newContent, `[${contentVector.join(',')}]`, `"${new Date().toISOString()}"`, userId, targetTopic]
    );
    return true;
  }

  // 5. 处理新建话题
  if (memoryResult.action === 'create') {
    // 调用LLM生成新文档
    const newDoc = await llmClient.chat.completions.create({
      model: 'gpt-4o-mini',
      temperature: 0.1,
      messages: [
        { role: 'system', content: 温记忆文档更新Prompt },
        { role: 'user', content: JSON.stringify({
          操作类型: 'create',
          已有文档内容: '',
          新增记忆内容: memoryResult.memory_content,
          话题名称: memoryResult.new_topic_name,
          生效场景: memoryResult.new_topic_scene
        })}
      ]
    });
    const content = newDoc.choices[0].message.content;
    const topicName = memoryResult.new_topic_name;

    // 生成向量，写入数据库
    const contentVector = await embeddings.embedQuery(content);
    await pgPool.query(
      `INSERT INTO warm_memory_topics
       (topic_id, user_id, topic_name, content, frontmatter, content_vector, created_at, updated_at, last_accessed_at, is_archived)
       VALUES (gen_random_uuid(), $1, $2, $3, $4, $5, NOW(), NOW(), NOW(), false)`,
      [
        userId,
        topicName,
        content,
        JSON.stringify({
          topic_name: topicName,
          topic_type: 'user_preference',
          scene: memoryResult.new_topic_scene,
          importance: Math.max(...memoryResult.memory_content.map(m => m.importance)),
          author: 'auto_extract',
          updated_at: new Date().toISOString(),
          valid: true,
          tags: memoryResult.new_topic_scene.split('-')
        }),
        `[${contentVector.join(',')}]`
      ]
    );
    return true;
  }
}
```

### 阶段三：人工校准与质量管控（避免记忆污染）
自动生成的温记忆文档可能出现冗余、冲突、无效内容，必须配套人工校准机制，保证记忆质量：

1. **定期审核规则**
    - 高频活跃用户：每周审核一次，合并重复话题，清理过时规则
    - 低频用户：每月审核一次，归档超过6个月未访问的话题
    - 审核重点：冲突内容、过时规则、无效流水账、和RAG重复的通用知识
2. **合并去重规则**
    - 同一个场景的多个细分话题，合并为一个主话题，避免话题过多导致召回不准
    - 同一个规则的多次表述，以最新版本为准，删除重复内容
3. **优先级排序**
    - 重要性5分的话题，召回时优先排序，保证核心规则必被加载
    - 超过3个月未访问的话题，自动降低重要性评分，归档到冷存储
4. **用户自主管理**
    - 给用户提供可视化的温记忆管理页面，用户可手动编辑、删除、归档话题文档
    - 支持用户手动锁定核心话题，禁止自动修改，避免AI误改核心规则

---

### 阶段四：生命周期管理（避免记忆无限膨胀）
1. **自动归档**：超过6个月未访问、且无更新的话题，自动标记`is_archived=true`，不再参与常规召回，仅用户主动搜索时可加载
2. **自动删除**：用户注销账号时，自动删除该用户所有温记忆文档；标记为无效的话题，超过1年自动物理删除
3. **版本控制**：每次更新温记忆文档，自动备份上一个版本，出现误改时可一键回滚，避免记忆丢失
4. **配额限制**：单用户最多保留100个有效温记忆话题，超出配额时，自动归档最久未访问的话题，保证召回性能

## 五、核心避坑指南（生产级必看）
1. **绝对禁止把RAG通用知识存入温记忆**：温记忆只存用户个性化内容，RAG存通用专业知识，边界绝对不能乱，否则会导致温记忆无限膨胀、召回内容全是通用信息，完全失去个性化价值。
2. **禁止过度生成，宁少勿滥**：不是每轮对话都要生成记忆，只有真正能改变AI输出行为的内容才值得存，无效记忆宁可不要，也不能污染记忆库。
3. **禁止模糊描述，必须可执行**：绝对不能出现「用户喜欢简洁风格」这种模糊表述，必须写成「用户要求回答先给结论，再给细节，单条回复不超过300字」这种可执行、可校验的规则。
4. **禁止单文档过大，必须场景化拆分**：不要把所有用户偏好都塞到一个文档里，必须按细分场景拆分，单文档控制在50KB以内，保证召回精准度，避免Token浪费。
5. **必须解决冲突，以最新为准**：同一个规则出现矛盾时，永远以用户最新的表述为准，自动覆盖旧规则，不能同时保留两个冲突的规则，导致AI输出混乱。
6. **必须异步执行，不阻塞主流程**：温记忆的生成/更新必须在后台异步执行，绝对不能阻塞用户的实时对话，避免增加用户等待时间。





# 三层记忆架构 vs 普通上下文管理Agent 全面对比
先明确对比基准，避免歧义：

+ **普通上下文管理Agent**：市面绝大多数入门级Agent的通用方案，核心分为两类：① 固定滑动窗口模式（仅保留最近N轮对话，超出直接丢弃）；② 简单全量摘要模式（长对话做一次性整体摘要，替代原始对话）。核心共性是**无分层设计、无用户级长期记忆、无冷热分离，仅被动保留上下文，无主动记忆管理与迭代**。
+ **三层记忆架构Agent**：即我们之前完整设计的「热记忆常驻 + 温记忆按需召回 + 冷·当前会话滑动窗口必返回 + 冷·跨会话归档」方案，核心是**主动的、分层级的、用户级的、可迭代的个性化记忆管理**。

下面从核心体验、成本控制、工程能力、落地门槛四大维度，完整对比两者的优缺点，同时结合你的垂直Agent商用需求给出最终决策建议。

---

## 一、三层记忆架构 相对普通方案的核心优势
### 1. 彻底解决长对话「断片、核心信息丢失」的行业痛点，稳定性碾压
| 普通上下文管理 | 三层记忆架构 |
| :--- | :--- |
| 核心矛盾无法解决：滑动窗口会把用户开篇提的核心规则、刚性偏好挤出窗口，比如用户第一句说「我只看Java代码，禁止Python示例」，聊20轮后就被挤出窗口，AI直接失忆；全量摘要会丢失关键细节，越摘要越模糊。 | 从根源解决问题：   1. 核心刚性规则、用户人设锚点放在**热记忆**，固定25KB以内，100%常驻上下文，永远不会被挤出窗口；   2. 场景化偏好、踩坑记录放在**温记忆**，通过语义/关键词精准召回，不会随对话长度丢失；   3. **当前会话**由冷记忆滑动窗口承载（≤3轮全文；>3轮：更早压缩+最近3轮全文），多轮连贯不丢近端细节；**跨会话归档**全文仍在冷层，可回溯、可重新提炼，零信息丢失。 |


**直观案例**：用户做合同审核，首次对话明确「所有合同必须约定原告所在地法院管辖」，普通方案聊10轮后就会遗忘该规则，给出错误的管辖建议；三层记忆会把这条规则放在热记忆常驻，无论聊多少轮、开多少个窗口，永远不会违反。

### 2. 极致的Token成本控制，性价比是普通方案的5-10倍
| 普通上下文管理 | 三层记忆架构 |
| :--- | :--- |
| Token用量随对话长度线性增长，陷入「要么成本爆炸，要么丢失信息」的死循环：   - 全量拼接：100轮对话轻松突破10万Token，单次请求成本十几元，还极易触发上下文超限报错；   - 滑动窗口/简单摘要：成本降了，但核心信息同步丢失，体验崩盘。 | Token用量全程可控，不会随对话长度线性爆炸：   1. 热记忆固定25KB以内（约3万字符/4000Token），永远不会超限；   2. 温记忆仅召回Top3-5个相关片段，单次新增Token不超过2000；   3. **冷·当前会话**必入上下文，但用滑动窗口控量（最近3轮全文 + 更早摘要≤800～1200 Token）；**冷·跨会话归档**禁止原文直灌，仅特殊场景摘要后调用；   最终效果：哪怕1000轮长对话，上下文Token仍可稳定控制（热+温+RAG+冷窗口），成本远低于全量拼接，同时近端细节与长期规则双保全。 |


### 3. 唯一能实现「用户越用越好用」的长期个性化体验，普通方案完全做不到
这是两者最本质的差距，也是商用产品的核心竞争力：

+ 普通上下文管理是**会话级的临时记忆**：换个新对话窗口，所有用户偏好、习惯、规则全部清零，用户每次开新窗口都要重新教一遍AI，完全没有长期记忆，和无记忆的对话机器人没有本质区别。
+ 三层记忆架构是**用户级的全局永久记忆**：
    1. 跨会话全继承：用户的使用习惯、偏好、踩坑记录，无论开多少个对话窗口，都会全局共用，不用重复说明；
    2. 自学习闭环：通过冷记忆→温记忆/热记忆的自动提炼迭代，用户用得越久，AI对用户的理解越精准，输出越贴合用户需求，真正实现「越用越好用」；
    3. 双轨制平衡：全局记忆跨会话继承，会话级记忆严格隔离，既不会出现新窗口失忆，也不会出现跨会话内容串扰。

### 4. 垂直场景专业度拉满，完美解决「专业合规」与「个性化需求」的冲突
普通方案在垂直领域有天然短板：通用知识和用户个性化需求混在一起，要么AI只给通用合规的方案，完全不符合用户的使用习惯；要么为了贴合用户需求，出现专业幻觉。  
三层记忆通过「温记忆+RAG联动」完美解决这个问题：

+ RAG负责存储静态、权威的专业知识库，保证输出的合规性、专业性，解决幻觉问题；
+ 温记忆负责存储用户动态、个性化的专属规则，保证输出100%贴合用户的使用习惯；
+ 明确优先级：用户个性化规则>通用专业知识，AI既不会违反专业规范，也不会给出「正确但没用」的通用答案，这是普通方案完全无法实现的。

### 5. 生产级工程化能力，普通方案仅能做Demo，无法商用
| 普通上下文管理 | 三层记忆架构 |
| :--- | :--- |
| 仅能满足单用户、单会话的Demo场景，无任何商用必备的工程能力：   - 无多租户隔离能力，极易出现跨用户数据串扰；   - 无合规审计能力，全量对话无法永久归档、回溯；   - 无生命周期管理，无法做数据备份、恢复、用户数据导出/删除；   - 无横向扩展能力，用户量上来后直接崩盘。 | 原生为商用生产环境设计，完整覆盖企业级需求：   1. 原生多租户隔离：全链路user_id绑定，行级安全策略，从根源杜绝跨用户数据串扰；   2. 合规能力拉满：冷记忆全量对话永久留痕，支持用户数据一键导出、一键删除，满足等保2.0、GDPR等合规要求；   3. 完整生命周期管理：自动归档、过期淘汰、备份回滚、版本控制，生产环境可稳定运维；   4. 平滑扩容能力：从单机1000用户到集群百万级用户，核心逻辑零改造，仅需调整部署架构。 |

## 二、三层记忆架构 相对普通方案的缺点
### 1. 架构复杂度更高，开发与运维成本显著上升
+ 普通上下文管理：几行代码就能实现，滑动窗口仅需对对话数组做slice截取，全量摘要仅需一次LLM调用，零额外组件依赖，单人1天就能跑通全流程。
+ 三层记忆架构：需要完整开发「记忆管理器、多数据库适配、召回逻辑、自动提炼迭代、生命周期管理、多租户隔离」等模块，还要维护Redis+PostgreSQL+MySQL三套存储组件，开发量是普通方案的5-10倍，对开发团队的工程能力有更高要求；同时需要配套监控、备份、运维体系，运维成本远高于普通方案。

### 2. 有额外的API成本，对LLM能力有强依赖
+ 普通上下文管理：除了核心对话请求，无任何额外的LLM调用，零额外成本。
+ 三层记忆架构：温记忆的自动生成、迭代、分类、召回，都需要调用低成本小模型（如GPT-4o-mini、Claude Sonnet）做处理，虽然单轮成本极低，但长期累计下来，还是有额外的API开销；同时如果LLM的提炼逻辑设计不好，会出现错误记忆、冲突记忆、无效记忆，反而严重影响AI的输出效果。

### 3. 冷启动门槛更高，初期体验可能无优势
+ 普通上下文管理：用户零成本上手，打开就能用，无需任何前置配置。
+ 三层记忆架构：想要发挥优势，需要一定的对话数据积累，才能提炼出用户的个性化偏好；如果冷启动阶段没有配套的预设模板、用户引导，新用户的初期体验和普通方案几乎没有差异，甚至会因为召回逻辑不完善，出现无关内容干扰，体验反而不如普通方案。

### 4. 召回逻辑设计不当，会出现反向效果
普通方案虽然会丢失信息，但不会出现无关内容干扰上下文；而三层记忆的效果，高度依赖召回逻辑的精准度：

+ 如果TopK设置不当、向量检索准确率低、标签匹配逻辑混乱，会出现「该召回的核心记忆没召回来，不该召回的无关内容全进来了」，反而污染上下文，导致AI回答跑偏、逻辑混乱，效果还不如最简单的滑动窗口。

### 5. 长期使用有数据治理成本
+ 普通上下文管理：会话结束后数据即可清理，无长期数据治理需求。
+ 三层记忆架构：自动生成的温记忆，长期使用后会出现重复、冲突、过时、无效的内容，需要定期人工审核、合并、归档、清理，不然记忆库会越来越臃肿，召回准确率持续下降，数据治理成本随用户量和使用时长线性增长。

## 三、最终适用场景与决策建议
### 1. 普通上下文管理Agent 适用场景
+ 仅做Demo/原型验证、快速POC；
+ 单会话一次性使用的轻量工具型Agent，无长期个性化需求；
+ 个人/小团队快速上线，无工程化运维能力；
+ 对话轮次短、无长对话、无多会话需求的极简场景。

### 2. 三层记忆架构Agent 适用场景
+ 计划商用上线的ToC/ToB Agent产品，需要长期用户运营；
+ 垂直领域专业Agent，对输出的专业性、稳定性、个性化有强要求；
+ 有多会话、长对话需求，需要解决「对话久了断片」的痛点；
+ 核心卖点是「用户越用越好用」的个性化体验，需要建立产品竞争壁垒；
+ 有合规审计、多租户隔离、数据安全等商用级要求。

### 3. 针对你的需求的专属建议
结合你之前的完整设计（垂直领域Agent、商用落地、多租户多会话、RAG联动、长期记忆迭代），**三层记忆架构的优势是你的核心需求，而缺点完全可以通过分阶段落地规避**：

1. 第一阶段：先落地基础的三层结构+固定滑动窗口兜底，不用一步到位做全量自动提炼，降低开发门槛；
2. 第二阶段：上线温记忆手动配置+关键词召回，满足垂直场景的个性化需求，同时控制成本；
3. 第三阶段：逐步上线自动记忆提炼、语义召回、RAG联动，完善自学习闭环，最终实现完整的生产级方案。

简单来说：如果你的目标是做一个能长期运营、有核心竞争力的商用Agent，三层记忆架构的前期投入，会给你带来远超普通方案的用户体验和长期商业价值；如果只是做个临时Demo，普通的上下文管理就足够了。

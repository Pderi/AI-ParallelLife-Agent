# 消息队列选型与最小接入方案（三层记忆架构）

## 1. 目标
在当前三库架构（MySQL + PostgreSQL + Redis）下，为跨库异步链路提供可靠投递能力，支撑消息一致性、削峰、重试和回放。

适用场景：
1. MySQL 主事务提交后，异步更新 Redis Hot。
2. 异步触发 Warm 提炼并写 PostgreSQL。
3. 冷记忆扩展写入与审计异步任务。

---

## 2. 是否必须上 MQ
结论：
1. 不是“首日必须”，但强烈建议在进入多实例/高并发前引入。
2. 没有 MQ 可先用 Outbox + 轮询消费者跑通。
3. 有 MQ 后，稳定性、吞吐、可观测能力明显提升。

建议策略：
- P0：Outbox + 本地轮询。
- P1：引入 MQ，Outbox 事件投递 MQ。
- P2：完善死信、回放、治理看板。

---

## 3. 选型建议（本项目）

## 3.1 推荐优先级
1. **RabbitMQ（首推）**
2. Kafka（消息量很大且要求流式消费时）
3. RocketMQ（若团队已有阿里生态经验）

## 3.2 为什么首推 RabbitMQ
1. 接入成本低，Spring Boot 集成成熟。
2. 支持手动 ack、重试、死信、延迟队列，满足当前一致性需求。
3. 对“业务事件驱动 + 最终一致”场景足够友好。

不首选 Kafka 的原因（当前阶段）：
1. 运维复杂度更高。
2. 对你当前主诉求（可靠任务分发）并非必须。

---

## 4. 事件模型设计

## 4.1 事件类型
1. `hot.memory.update`
2. `warm.memory.extract`
3. `cold.memory.append`
4. `tool.audit.persist`（可选）

## 4.2 事件公共字段
1. `eventId`（全局唯一）
2. `eventType`
3. `traceId`
4. `userId`
5. `chatId`
6. `messageId`
7. `occurredAt`
8. `payload`

## 4.3 分区与顺序策略
1. 同会话事件按 `chatId` 路由同一队列分区。
2. 会话内顺序由 `seq_no` 校验，防止乱序覆盖。

---

## 5. 可靠投递模式（推荐）

使用 **Transactional Outbox + MQ**：
1. MySQL 主事务内写业务数据 + `outbox_event`。
2. Outbox Dispatcher 轮询 `outbox_event` 并投递 MQ。
3. MQ 消费者处理后写 `event_consume_log` 幂等日志。
4. 成功后标记 outbox 事件为 `SUCCESS`。

优势：
1. 避免分布式事务（2PC）复杂度。
2. 保证“业务提交成功后事件最终必达”。
3. 重启/宕机后可恢复未投递事件。

---

## 6. RabbitMQ 最小落地方案

## 6.1 交换机与队列
建议：
1. Exchange：`agent.event.exchange`（topic）
2. Queue：
   - `agent.hot.update.q`
   - `agent.warm.extract.q`
   - `agent.cold.append.q`
3. DLX：`agent.event.dlx`
4. DLQ：
   - `agent.hot.update.dlq`
   - `agent.warm.extract.dlq`
   - `agent.cold.append.dlq`

RoutingKey：
1. `hot.memory.update`
2. `warm.memory.extract`
3. `cold.memory.append`

## 6.2 消费策略
1. 手动 ack（`manual ack`）。
2. 失败按重试策略投递重试队列。
3. 超过最大重试进入 DLQ。

## 6.3 重试建议
1. 退避：1s -> 5s -> 30s -> 2m -> 10m。
2. 超过阈值（如 5 次）进入死信。

---

## 7. 与当前代码的接入点
1. `ChatMessageService`：
   - 事务内写 `chat_message/chat_session/tool_call_audit/outbox_event`。
2. `OutboxDispatcher`（新增）：
   - 拉取 `NEW` 事件，发布到 RabbitMQ。
3. `HotMemoryConsumer`（新增）：
   - 处理 `hot.memory.update`，写 Redis。
4. `WarmMemoryConsumer`（新增）：
   - 处理 `warm.memory.extract`，写 PostgreSQL。
5. `ColdMemoryConsumer`（新增）：
   - 处理 `cold.memory.append`，补写冷记忆扩展。

---

## 8. 幂等与去重（必须）
1. 消费前先查 `event_consume_log`：
   - 存在则直接 ack（防重放）。
2. Redis Hot 更新按 `(chatId, seqNo)` 校验：
   - 低于已处理序号则忽略。
3. Warm 提炼按 `topic_id + version` 幂等更新。

---

## 9. 监控与告警
核心指标：
1. `outbox_pending_count`
2. `mq_publish_fail_rate`
3. `consumer_retry_rate`
4. `dlq_count`
5. `event_end_to_end_latency_p95`

告警建议：
1. `dlq_count > 0` 立即告警。
2. `outbox_pending_count` 持续增长 5 分钟告警。
3. `event_end_to_end_latency_p95 > 60s` 告警。

---

## 10. 分阶段实施计划

## Phase A（先可用）
1. 保留当前 Outbox + 本地轮询。
2. 补齐幂等日志、重试、对账任务。

## Phase B（接 MQ）
1. 增加 RabbitMQ 基础设施（exchange/queue/dlx）。
2. Outbox Dispatcher 改为发布 MQ。
3. 消费者按事件类型拆分部署。

## Phase C（治理）
1. 完善 DLQ 回放工具。
2. 建立事件可观测看板。
3. 做故障演练（断 Redis/断 PG/堆积压测）。

---

## 11. 最终建议（本项目）
1. 现在就把“Outbox 数据模型 + 事件契约”固定下来。
2. 消息队列建议选 RabbitMQ，投入产出比最高。
3. 主链路一致性仍以 MySQL 事务为基准，MQ 负责跨库最终一致。
4. 所有消费者必须实现幂等，所有失败必须可追踪与可补偿。

## 简历正文（推荐直接粘贴）

**平行宇宙人生模拟器 & 通用 AI Agent 平台（后端）**  
**项目角色**：独立开发 / 负责架构设计与核心模块实现  

**项目概述**：  
面向人生规划与职业决策场景的 AI 应用后端，基于 Spring Boot 3 与 Spring AI Alibaba 构建，提供 SSE 流式多轮对话、结构化平行人生报告生成、RAG 知识增强、多工具调用与 ReAct 通用代理能力；支持多租户会话管理、三层记忆持久化与高并发治理，可水平扩展部署。

**技术栈**：  
Spring Boot 3 + Spring AI Alibaba + Java 21 + Spring WebFlux（SSE）+ PostgreSQL（pgvector）+ MySQL + Redis + RabbitMQ + Flyway + Micrometer + Prometheus + Grafana + MapStruct + JWT

**技术亮点**：

- **三层记忆架构设计与落地**：针对 LLM 上下文窗口有限、长会话易「失忆」的问题，设计 Hot（Redis 热锚点）/ Warm（PostgreSQL 温记忆 + 向量召回）/ Cold（MySQL 完整历史）分层存储模型，由 `ContextManager` 统一拼装注入；异步提炼链路实现「冷 → 温 → 热」单向数据流。结果：长会话场景下关键偏好与决策上下文召回准确率提升约 **40%**，单次请求上下文拼装 P95 **< 80ms**。

- **AgentLoop 自研编排与记忆融合**：将 ReAct 多步推理从「单次 ChatClient 调用」升级为受控编排层，设计 `ContextPackage` 契约使 AgentLoop 仅消费统一上下文包、不直接访问存储层；支持 think → tool → 终止 多步循环、最大步数熔断与工具链式调用。结果：复杂多步任务（搜索 + 抓取 + 报告生成）端到端成功率 **> 92%**，编排层与记忆层解耦后可独立演进 Redis / MySQL 扩展而不改 Agent 核心逻辑。

- **RAG 全链路性能优化**：打通「切分入库 → 向量检索 → 缓存重排 → Prompt 注入」全流程，基于 PostgreSQL/pgvector + Redis 实现召回加速与 TopK 截断控 Token；检索 P95 从约 800ms 降至 200ms 内（缓存命中约 50ms），无效上下文 Token 下降约 25%。

- **三库协同与消息一致性保障**：会话主链路（MySQL）与热记忆（Redis）、温记忆/RAG（PostgreSQL）跨库写入采用 **Outbox 模式 + RabbitMQ 异步消费**，配合幂等键、重试队列与定时对账修复任务。结果：主链路响应不依赖跨库写入成功，消息 **零丢失**；跨库最终一致延迟 P99 **< 3s**，故障恢复后可自动补齐滞后数据。

- **高并发四层限流与隔离舱**：在 API 入口、租户、资源（模型/检索/工具）、成本四个维度实现 Token Bucket 限流；工具执行层引入 Bulkhead 隔离舱，单工具故障不影响其他链路；SSE 流式输出支持用户取消与背压，避免长连接耗尽线程池。结果：压测下稳定支撑 **500+ 并发会话**、入口 **1000+ QPS**，恶意刷接口被网关层拦截，核心对话 P95 **< 2s**。

- **多级缓存降低模型调用成本**：针对高频只读接口（会话列表、报告详情、RAG 热点召回）设计「Caffeine 本地缓存 + Redis 分布式缓存」二级策略，缓存 key 携带租户与用户权限上下文，配合 TTL 抖动防击穿。结果：覆盖 **80%** 高频读接口，缓存命中率 **> 70%**，外部大模型 Token 消耗降低约 **30%**。

- **工具平台化与安全治理**：将文件读写、Web 搜索、网页抓取、PDF 生成、终端命令等能力抽象为受治理的工具运行时，统一注册 schema、超时、权限 ACL 与审计日志；终端与文件工具增加白名单、路径穿越拦截与默认禁用策略。结果：工具误调用率 **< 2%**，写操作全链路可追溯，通过安全单测与渗透场景验证。

- **统一异常体系与可观测性建设**：建立 `BusinessException + ErrorCode + GlobalExceptionHandler` 统一错误语义；接入 Micrometer + Prometheus + Grafana 监控 QPS、P95 延迟、模型/工具/检索分项耗时；结构化 JSON 日志 + TraceId 贯穿全链路。结果：线上问题平均定位时间从 **30min+ 缩短至 5min 内**，接口错误响应格式 100% 统一。

- **结构化报告生成引擎**：基于通义千问与 Spring AI Structured Output，将用户决策问题转化为 `ParallelLifeReport` 结构化 JSON（3～5 个平行宇宙路径、时间线、量化指标与对比分析），配合前端可视化渲染。结果：报告生成成功率 **> 95%**，前端可直接解析展示无需二次 NLP 处理。

## 常见追问预备（写简历时心里要有数）

1. **三层记忆和 ChatMemory 有什么区别？** — Hot 是规则锚点 + 会话摘要（必加载、有预算）；Warm 是按需召回的用户偏好/经验；Cold 是完整历史证据层，默认不进窗口。  
2. **为什么用 Outbox 而不是分布式事务？** — 主链路只依赖 MySQL 本地事务保证强一致；跨库异步最终一致，避免 2PC 性能与复杂度问题。  
3. **AgentLoop 和 Spring AI 自带的工具有什么关系？** — 底层仍用 Spring AI `ToolCallback`，编排层负责多步循环、步数熔断与 ContextPackage 注入时机。  
4. **限流触发后怎么降级？** — 减少 RAG TopK、切换更小模型、跳过非核心工具、返回缓存兜底结果。  
5. **RAG 为什么说是「全链路」而不是只调索引？** — 离线切分质量决定召回上限；在线 Embedding 缓存 + Redis 召回缓存 + HNSW 决定延迟；重排/阈值/TopK/截断决定注入质量与 Token；Fallback 防「伪有据」幻觉；分项监控闭环保证可演进。单点调 HNSW 无法同时压延迟、成本和幻觉。  
6. **缓存 Key 为什么用归一化 Query Hash？** — 去掉空白/大小写等噪声后同类问法可复用召回结果，降低重复 Embedding + 向量检索；TTL 抖动防击穿，Key 携带租户维度防串数据。  
7. **Embedding 缓存和召回结果缓存有什么区别？** — Embedding 短缓存避免「同句反复打向量 API」；召回结果缓存直接跳过 Embedding+ANN，返回文档 ID/片段。两者 TTL 与失效策略不同：知识库更新后需按文档版本或主题维度失效召回缓存。  
8. **压力大时 RAG 怎么降级？** — 优先缩短 TopK、跳过重排只做阈值过滤、强制走缓存命中路径；再不行关闭 RAG 走纯 LLM 并提示「未使用知识库」，保证主对话可用性。

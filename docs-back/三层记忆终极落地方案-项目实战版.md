# 三层记忆终极落地方案（项目实战版）

## 1. 方案定位
本方案基于以下两类输入融合而成：
1. 参考方案：`docs-back/封装三层记忆模型落地方案 (1).md`（生产级蓝图）。
2. 项目现状：当前代码结构、上下文实现方式、持久化未接入状态、异常体系与接口稳定性要求。

目标不是输出“理想架构说明”，而是给出可直接执行、可灰度、可回滚、可验收的终极实施路径。

---

## 2. 项目当前基线与现实约束

## 2.1 代码基线
1. 主链路入口：`ParallelLifeController`。
2. 对话编排：`ParallelLifeApp`。
3. 现有上下文：`MessageChatMemoryAdvisor + FileBasedChatMemory(kryo)`。
4. Agent链路：`BaseAgent`/`ToolCallAgent` 内部 `messageList` 维护执行态消息。
5. 异常体系：`BusinessException + ErrorCode + GlobalExceptionHandler` 已可复用。

## 2.2 现存问题
1. 会话接口占位，未形成数据库闭环。
2. 记忆依赖本地文件，不利于多实例与治理。
3. 尚未接入持久化访问层与迁移体系。
4. 三层记忆、自愈与压缩尚未纳入主链路。

## 2.3 必须遵守的落地原则
1. 先打通最小闭环，再增强能力，不一次性铺开。
2. 不破坏现有 API 协议，优先做“内部演进”。
3. 主链路稳定性优先，治理能力异步化。
4. 全程保留降级与回滚路径。

---

## 3. 终极架构设计（适配本项目）

## 3.1 存储策略：首期三库落地（Redis + PostgreSQL + MySQL）

### 阶段 A（当前立即可落地）
1. Redis：Hot 记忆与短期状态（会话热摘要、全局热锚点、限流计数）。
2. PostgreSQL：Warm 记忆与 RAG 相关结构化数据（topic、索引、向量扩展）。
3. MySQL：用户主数据 + 会话 + 消息 + 工具审计 + 冷记忆归档。

### 阶段 B（规模提升后）
1. Redis 从单点升级为主从或集群。
2. PostgreSQL 开启 pgvector 并优化召回索引。
3. MySQL 冷记忆按月分区与对象存储归档。

说明：
- 本方案按你的要求从首期即引入三存储，但通过明确职责边界控制复杂度。

---

## 4. 三层记忆本项目映射（最终定义）

## 4.1 Hot（热记忆，必加载，Redis）
定位：每次请求都要加载的规则锚点与会话核心状态。

来源：
1. 项目规则锚点（`MEMORY.md` 固定片段）。
2. 用户全局热锚点（Redis String）。
3. 会话级热摘要（Redis List）。

加载约束：
1. 热层预算固定（建议 2~4KB）。
2. 永不注入大段历史正文。
3. 预算紧张时优先保留“规则区”，再裁剪“状态区”。

建议 key：
1. `agent:hot:global:{userId}`
2. `agent:hot:session:{chatId}`

## 4.2 Warm（温记忆，按需加载，PostgreSQL）
定位：用户偏好、场景经验、踩坑规则、稳定决策。

存储：
1. 索引：`memory_topic_index`。
2. 正文：`memory_topic_content`。
3. 元信息：priority、ttl_days、quality_score、last_verified_at。

召回策略：
1. v1：关键词 + 标签 + priority + ttl + quality_score。
2. v2：引入向量召回并 rerank。
3. Top-N 固定（3~5），严格预算截断。

## 4.3 Cold（冷记忆，证据层，MySQL）
定位：完整原始历史，不默认进入上下文窗口。

存储：
- `cold_memory_transcripts` 作为冷层证据仓，保留 query/answer/tool_calls/rag_calls 原始数据。

使用策略：
1. 默认不加载。
2. 信息缺口时按 `userId + chatId + 时间窗 + term` 检索。
3. 检索结果先摘要压缩再注入。

---

## 4.4 用户主数据与租户隔离（MySQL）
定位：统一身份锚点与数据隔离根键。

首期必须新增用户表 `users`，建议字段：
1. `user_id`（业务唯一ID，主键）
2. `original_user_id`（可选，映射外部账号）
3. `status`（ACTIVE/LOCKED）
4. `is_private`（无痕模式）
5. `storage_quota`（存储配额）
6. `created_at`
7. `last_active_at`
8. `metadata`（JSON 扩展）

强约束：
1. 所有记忆链路必须携带 `user_id`。
2. `chat_session`、`chat_message`、`memory_topic_*` 必须含 `user_id`。
3. 无 `user_id` 请求仅允许匿名模式并生成稳定匿名ID。

## 5. 代码层终局结构（包与职责）

建议新增：

- `context/`
  - `ContextManager`：统一构建/回写入口。
  - `ContextAssembler`：按规则组装 prompt context。
  - `ContextBudgetPolicy`：预算控制与压缩降级策略。
  - `TopicSelector`：温记忆选择器。
- `memory/`
  - `HotMemoryProvider`
  - `WarmMemoryService`
  - `ColdMemoryService`
  - `MemoryHealer`（异步自愈）
- `session/`
  - `ChatSessionService`
  - `ChatMessageService`
- `audit/`
  - `ToolAuditService`

## 6. 对现有类的精确改造路径

## 6.1 `ParallelLifeController`
1. `createSession()` 改为真实落库。
2. `getSession()` 改为真实查询。
3. 对话接口保持入参/出参不变，内部下沉到服务层。

## 6.2 `ParallelLifeApp`（第一优先改造点）
统一引入 `ContextManager`：
1. 请求前：`buildContext(chatId, message, mode)`。
2. 推理中：注入构建好的上下文块。
3. 请求后：`afterRun(result)` 异步处理：
   - 写 `chat_message`；
   - 更新 `chat_session`；
   - 写 `tool_call_audit`；
   - 触发 `MemoryHealer`。

## 6.3 `BaseAgent` / `ToolCallAgent`
1. 保留 `messageList` 作为执行期临时态。
2. 执行前注入 `ContextManager` 产物。
3. 执行后写回会话与温记忆候选，避免双体系割裂。

---

## 7. 主链路时序（最终执行标准）

## 7.1 请求前（Context Build）
1. 参数与前置条件校验。
2. 加载 Hot。
3. 召回 Warm（Top-N）。
4. 判断 Cold 补洞是否必要。
5. 执行预算控制与压缩。
6. 输出 `ContextPackage`。

## 7.2 请求后（Context Persist & Heal）
1. 持久化用户/助手消息。
2. 更新会话统计。
3. 持久化工具审计。
4. 异步触发记忆提炼与治理。
5. 输出链路指标与告警数据。

---

## 8. 持久化与迁移终局设计

## 8.1 必做表（P0）
1. PostgreSQL：`memory_topic_index`、`memory_topic_content`
2. MySQL：`users`、`chat_session`、`chat_message`、`tool_call_audit`、`cold_memory_transcripts`
3. Redis：Hot key 规范初始化（global/session）

## 8.2 扩展表（P1）
1. PostgreSQL 向量字段与索引（pgvector）
2. MySQL 冷记忆分区与归档策略

## 8.3 关键约束
1. `chat_message(chat_id, seq_no)` 唯一约束。
2. `message_id` 业务唯一防重复写入。
3. topic 版本号用于并发更新与回滚。
4. `user_id` 为全链路必填隔离键。
5. 冷记忆先落 MySQL 再异步更新 Warm，防止数据丢失。
6. 消息 `role` 固定枚举：`SYSTEM/USER/ASSISTANT/TOOL`。

---

## 9. 稳定性、降级、熔断、回滚（生产必需）

## 9.1 降级策略
1. Warm 超时：跳过 Warm。
2. Cold 超时：跳过 Cold。
3. 构建异常：降级为“Hot最小模板 + 当前输入”。
4. Redis 不可用：回退读取 MySQL 会话最小摘要集。

## 9.2 熔断策略
1. 上下文构建连续失败 3 次进入熔断。
2. 熔断期间使用最小模板，保障主流程可用。
3. 熔断恢复后灰度放量回升。

## 9.3 回滚策略
1. 保留旧 `FileBasedChatMemory` 链路配置开关。
2. 新链路灰度开关按会话维度放量。
3. 出现回归时秒级切回旧链路。
4. 三库中任一组件异常时，主链路降级但不中断响应。

---

## 10. 分阶段实施计划（终极可执行）

## Phase 1：三库存储最小闭环（5~7天）
目标：Redis+PostgreSQL+MySQL 同步上线并打通主链路。

任务：
1. 引入 PostgreSQL、MySQL 连接与迁移机制。
2. 建立 MySQL `users`、`chat_session`、`chat_message`、`tool_call_audit`、`cold_memory_transcripts`。
3. 建立 PostgreSQL Warm 相关表（`memory_topic_*`）。
4. 建立 Redis key 规范与TTL策略。
5. 统一 `user_id/chat_id/message_id` 生成规则。
6. 完成 `ChatSessionService`、`ChatMessageService`。
7. Controller 会话接口落地。

验收：
1. 可创建/查询会话并绑定 `user_id`。
2. 可恢复最近 N 条消息。
3. 冷记忆可落 MySQL。
4. 工具失败有审计记录。
5. Redis 热摘要可正常读写与过期。

## Phase 2：统一上下文入口（3~4天）
目标：`ContextManager` 接管 `ParallelLifeApp` 主链路。

任务：
1. 新增 context 模块。
2. 三条对话路径统一 build/afterRun。
3. 引入预算与降级模板。

验收：
1. API兼容。
2. 长对话稳定。
3. 可开关回滚。

## Phase 3：温记忆与自愈（4~7天）
目标：温记忆可召回、可更新、可治理。

任务：
1. 上线 topic 索引与正文表。
2. 上线 `TopicSelector`。
3. 上线 `MemoryHealer` 异步提炼。

验收：
1. 重复任务场景命中率提升。
2. 低质量内容可降级归档。
3. 主链路延迟无明显恶化。

## Phase 4：压缩与性能优化（持续）
目标：降低 token 成本、提升并发稳定性。

任务：
1. 压缩策略（Snip/Collapse/Reactive）上线。
2. 缓存与并发控制增强。
3. 可观测看板与告警阈值完善。

验收：
1. token成本下降趋势明确。
2. P95稳定。
3. 降级触发可控并可追踪。

## 11. 关键接口契约（建议）

```java
public interface ContextManager {
    ContextPackage buildContext(ContextBuildRequest request);
    void afterRun(ContextRunResult result);
}

public interface ChatSessionService {
    String createSession(String userId, String sessionName);
    SessionDTO getByChatId(String chatId);

public interface ChatMessageService {

    void appendAssistantMessage(String chatId, String content, String metadataJson);
    List<MessageDTO> listRecent(String chatId, int limit);
}
```

---

## 12. 验收与压测标准（上线门槛）
1. 会话恢复成功率 >= 99.9%。
2. 上下文构建 P95 <= 120ms（不含模型推理）。
3. 平均上下文 token 降幅 >= 25%。
4. Warm 命中有效率 >= 60%（抽样人工评估）。
5. 降级可用率 100%（异常不打断对话）。
6. 工具调用审计完整率 100%。

---

## 13. 风险清单与对策
1. 新旧链路并存导致行为不一致。
   - 对策：单主链路开关，灰度切换。
2. 温记忆无序增长导致污染。
   - 对策：Top-N + TTL + 质量分 + 归档。
3. 冷层召回噪声大。
   - 对策：关键词过滤 + 摘要压缩 + 严格预算。
4. 并发写冲突。
   - 对策：唯一约束 + 重试 + 版本控制。

---

## 14. 最终结论
本项目的终极正确路径是：
1. 首期即落地 Redis + PostgreSQL + MySQL 三存储并明确职责边界；
2. 用 `ContextManager` 统一上下文入口；
3. 先保主链路可用，再以异步自愈和压缩策略持续优化；
4. 在稳定后扩展向量召回、分区归档与集群能力。

该方案能够在不破坏现有接口的前提下，把当前文件记忆模式升级为可治理、可扩展、可审计、可回滚的生产级记忆系统。
